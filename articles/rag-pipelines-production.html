RAG Pipelines in Production: Beyond the Hype

Everyone talks about RAG like it's magic. Embed your documents, search for relevant chunks, generate an answer. Easy, right?

After running RAG in production for six months powering our KYC compliance system, I've learned it's more art than science. The theory is simple. The practice is full of edge cases, trade-offs, and decisions that dramatically impact quality.

Here's what nobody tells you about RAG until you're neck-deep in production issues at 2 AM.

The Problem: Compliance Questions at Scale

Our digital banking platform handles customer onboarding across 12 countries, each with different KYC and AML regulations. Support teams were constantly asking: "Does this document meet India's KYC requirements?" or "What's the minimum age for account opening in Germany?"

We had the answers buried in 2,000+ pages of regulatory documentation. Finding them meant searching through PDFs, cross-referencing regulations, and hoping you found the right section.

Enter RAG. The promise: Ask questions in natural language, get accurate answers grounded in our documentation.

The reality: It took us three months of iteration to get from "sometimes works" to "actually reliable."

The Basic Architecture

RAG Pipeline Architecture

1. Document Processing
PDFs → Clean Text → Chunking
2. Embedding
Chunks → Vector Embeddings
3. Vector Storage
Store + Index for Fast Search
4. Query Pipeline
Question → Search → Generate Answer

Looks straightforward on a diagram. In practice, each of these steps has 10 decisions that affect your results.

Lesson 1: Chunking is Harder Than It Looks

The first version of our system just split documents every 500 tokens. Simple. Fast. Terrible.

We'd get answers like: "According to Section 4, customers must provide..." — except Section 4 was about something completely different, and the actual requirement was in Section 7.

The problem? Naive chunking breaks context.

Imagine splitting this sentence mid-way: "Customers under 18 years old [CHUNK BOUNDARY] are not eligible for premium accounts." Now one chunk says customers under 18 are fine, and another says they're not eligible. Both chunks are technically accurate, but neither tells the full story.

We fixed this by implementing semantic chunking:

  • Respect document structure (don't split mid-sentence or mid-paragraph)
  • Keep related content together (regulatory requirements with their exceptions)
  • Add metadata (section headers, document title, country) to each chunk
  • Use overlapping chunks (last 100 tokens of one chunk = first 100 tokens of next)

Retrieval accuracy jumped from 62% to 89% just by chunking smarter.

Lesson 2: Embeddings Are Not Created Equal

We started with OpenAI's text-embedding-ada-002. It worked okay for general questions but struggled with domain-specific terminology.

"What is PEP screening?" would return chunks about "pepper screening" (a food safety term) instead of "Politically Exposed Person screening" (a KYC term).

The fix wasn't switching embedding models (though we tried). It was fine-tuning our retrieval:

  • Build a domain-specific glossary as a vector lookup table
  • Use hybrid search (vector similarity + keyword matching)
  • Add query expansion (transform "PEP" into "Politically Exposed Person")
  • Rerank results using a cross-encoder model

Hybrid search was the game-changer. Pure vector search is great for semantic similarity, but it misses exact matches. Combining both gives you the best of both worlds.

Lesson 3: Retrieval Matters More Than Generation

Here's a surprising truth: 80% of RAG quality comes from retrieval, not generation.

If you retrieve the wrong chunks, even GPT-4 can't save you. It'll confidently generate an answer based on irrelevant context.

We learned this the hard way when our system told a support agent that German customers needed to provide a "passport or driver's license" for KYC. Technically true, but incomplete — German regulations also accept national ID cards, which most Germans actually use.

Why? The retrieval only pulled 3 chunks, and the chunk mentioning national ID cards ranked 4th.

The solution: retrieve more, rank better.

  • Retrieve top 10 chunks (not just top 3)
  • Rerank them using a specialized cross-encoder
  • Pass top 5 reranked chunks to the LLM
  • Include a confidence score for each chunk

This added 200ms to latency but cut incorrect answers by 60%.

Lesson 4: Metadata is Your Friend

Early on, we'd get questions like "What are the age requirements?" — but age requirements vary by country and account type.

Without context, the system would return a random answer, sometimes from the wrong country's regulations.

We fixed this by treating metadata as a first-class citizen:

  • Document metadata: country, regulation type, last updated date
  • Chunk metadata: section header, page number, document title
  • Query metadata: user's role, customer's country, account type

Now when someone asks "What are the age requirements?", the system uses their context (they're supporting a German customer) to filter chunks before semantic search.

This is RAG 2.0: context-aware retrieval.

Lesson 5: Monitoring is Non-Negotiable

In production, things drift. Documents get updated, regulations change, user questions evolve.

We monitor:

  • Retrieval metrics: How often do retrieved chunks actually contain the answer? (We sample 10% of queries for manual review)
  • Confidence scores: When the system is unsure (low confidence), we flag it for human review
  • Fallback rate: How often does the system say "I don't know"?
  • User feedback: Thumbs up/down on answers

When we see retrieval accuracy drop below 85%, it's usually a sign that new documents were added without re-embedding the collection.

Lesson 6: Know When to Say "I Don't Know"

The most dangerous thing an AI system can do is confidently give wrong answers.

We explicitly prompt our LLM:

"If the retrieved context doesn't contain enough information to answer the question accurately, say 'I don't have enough information to answer this question.' Do NOT make up answers."

And we enforce this with confidence thresholds. If the top-ranked chunk scores below 0.7, we return "Not enough information found" instead of generating an answer.

False negatives (saying "I don't know" when we could answer) are annoying. False positives (confidently giving wrong answers) are dangerous.

In banking, dangerous is unacceptable.

What We'd Do Differently

If I were building this system again from scratch, I'd:

  • Start with hybrid search, not pure vector search
  • Invest in evaluation early — build a test set of questions with known answers
  • Use a reranker from day one, not as an afterthought
  • Add human-in-the-loop feedback from the start — let users mark wrong answers
  • Build for observability — log everything, you'll need it for debugging

The Reality Check

RAG isn't magic. It's a powerful pattern, but it requires careful engineering to work reliably in production.

The good news? When it works, it's transformative. Our support team now answers compliance questions in seconds instead of minutes. Accuracy is above 90%. And the system keeps learning from feedback.

But getting there took work. If you're building RAG systems, budget time for iteration. The first version won't be production-ready, and that's okay.

"RAG isn't plug-and-play. It's a framework that needs tuning, monitoring, and continuous improvement."

Key Takeaways:

  • Chunking strategy dramatically impacts retrieval quality
  • Hybrid search (vector + keyword) beats pure vector search
  • 80% of quality comes from retrieval, not generation
  • Metadata enables context-aware, accurate retrieval
  • Monitor retrieval metrics, not just generation quality
  • Embrace "I don't know" — it's better than being confidently wrong
