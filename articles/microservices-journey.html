The Microservices Journey: When Breaking Things Apart Makes Sense

Three years ago, our banking platform was a Rails monolith handling everything from customer onboarding to compliance checks to payment processing. One codebase, one database, one deployment.

Today, it's 23 microservices orchestrated across AWS and Azure, each owned by a different team, each deployable independently.

This is the story of why we did it, what went spectacularly wrong, and what we'd do differently if we could start over.

The Monolith Wasn't The Problem (At First)

Let me be clear: our monolith wasn't bad. It was well-architected, had decent test coverage, and served us fine for years. We processed millions of transactions monthly without major incidents.

But three things changed:

  • Team size: We grew from 12 to 50+ engineers. Merge conflicts became daily battles.
  • Deployment frequency: Releasing meant coordinating 6 teams. Small features waited weeks for the next release window.
  • Technology constraints: Some features (like real-time fraud detection) needed different tech stacks. Forcing everything into Rails was becoming painful.

The breaking point came when a one-line config change in the KYC module took three weeks to deploy because it had to wait for unrelated payment features to finish testing.

"What if each team could deploy independently?" someone asked.

That's when we started exploring microservices.

Lesson 1: Start With Bounded Contexts

Our first mistake was trying to carve up the monolith by technology instead of business domains.

We created a "Database Service" that all other services called for data access. A "Notification Service" that handled all emails and SMS. An "Authentication Service" for all logins.

This was a disaster. Every feature change required coordinating multiple services. We'd just rebuilt the monolith, but with network latency.

We fixed this by following Domain-Driven Design principles. Instead of technical layers, we carved along business boundaries:

  • Customer Onboarding Service: Everything about getting customers started
  • KYC Verification Service: Identity verification and compliance
  • Payment Processing Service: Money movement and reconciliation
  • Fraud Detection Service: Real-time transaction monitoring

Each service owned its data, its business logic, and its deployment cycle. This made teams truly independent.

Lesson 2: The Database Question

One database per service or shared database? This debate nearly split the team.

We tried shared database first. Bad idea. Services coupled through database schemas. One team's schema change broke another team's queries. We were back to coordination hell.

We switched to database per service. Each service owned its database completely. No shared tables, no cross-service queries.

"But what about joins?" people asked.

We handled them through APIs or event sourcing. Yes, it's more code. Yes, it's slower than SQL joins. But the team independence was worth it.

Lesson 3: Observability Becomes Critical

Debugging the monolith was straightforward: check the logs, add a breakpoint, step through code.

Debugging microservices? A nightmare at first. A single customer onboarding flow touched 7 services. When something failed, good luck figuring out where.

We solved this with distributed tracing. Every request gets a trace ID that flows through all services. When something breaks, we can see the entire journey:

  • Request hits API Gateway (12ms)
  • Onboarding Service calls KYC Service (245ms)
  • KYC Service calls External ID Verification API (1.8s — aha! Bottleneck found)

Without tracing, we were flying blind. With it, debugging became manageable.

Lesson 4: Microservices Create Operational Overhead

Here's what nobody tells you: microservices multiply operational complexity.

The monolith: 1 deployment, 1 CI/CD pipeline, 1 monitoring dashboard, 1 log aggregator.

Microservices: 23 deployments, 23 pipelines, 23 dashboards, 23 log streams.

We invested heavily in standardization:

  • Service templates: New services start from a template with logging, monitoring, and deployment pre-configured
  • Shared infrastructure: Centralized logging (ELK stack), monitoring (Prometheus + Grafana), tracing (Jaeger)
  • Platform team: Dedicated team maintaining shared tooling and best practices

Without standardization, each team would build things differently, and operational chaos would reign.

Lesson 5: Not Everything Should Be a Microservice

We got microservice-happy and broke things up too much. We created a "Currency Conversion Service" that did one thing: convert amounts between currencies. It was 200 lines of code that could've been a library.

Now it's a service with its own deployment, monitoring, and API. Total overkill.

When to use microservices:

  • Different teams need to deploy independently
  • Different technology stacks are justified
  • Scaling requirements differ significantly
  • Business domains are naturally separated

When NOT to use microservices:

  • Your team is < 10 engineers
  • The domains aren't clearly separable
  • You don't have infrastructure for observability and deployment
  • It's just a utility function (make it a library instead)

What We Gained

After three years, was it worth it?

Yes. But not for the reasons you might think.

The win wasn't performance (actually worse due to network overhead). It wasn't cost savings (infrastructure costs went up).

The win was organizational velocity.

Teams can now deploy 20+ times per day instead of once per week. Features ship faster. Engineers feel ownership. Different teams can innovate with different technologies.

In banking, where compliance is king and downtime is unacceptable, that velocity is transformative.

"Microservices are an organizational strategy disguised as a technical architecture."

Key Takeaways:

  • Start with business domains, not technical layers
  • One database per service — embrace API calls over joins
  • Invest in observability before going distributed
  • Standardize infrastructure or face operational chaos
  • Not everything needs to be a microservice — know when to stop
