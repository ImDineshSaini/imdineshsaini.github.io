Leading AI Adoption: Getting Engineers Excited About LLMs

When I started the Engineering AI Hub at SBS, half the team was skeptical. "It's just autocomplete," they said. "It writes buggy code." "It'll replace us."

Six months later, we've built tools that reduced development effort by 30%. Engineers who were skeptical are now our biggest advocates. Here's how we turned skeptics into believers.

The Resistance Was Real

The first AI Hub meeting had 8 people. Five came out of obligation. The energy was... underwhelming.

I understood the resistance. Engineers had seen AI hype before. Every year, something is the "next big thing." Most fade into irrelevance.

LLMs felt different to me, but I couldn't expect everyone to just believe that. I needed to show, not tell.

Strategy 1: Start With Pain Points

I didn't start by teaching LLM theory. I started by asking: "What's annoying in your workflow?"

The answers came fast:

  • "Writing API documentation is tedious"
  • "Code reviews take forever for obvious stuff"
  • "Breaking down user stories into tasks is repetitive"
  • "Debugging error logs is time-consuming"

Perfect. Those became our first AI projects.

Strategy 2: Build Something Useful in Week 1

We built our first tool in a week: an API documentation generator.

Point it at a Ruby on Rails controller, it generates markdown docs with endpoints, parameters, and example responses. Not perfect, but 80% of the work done automatically.

Technical Implementation:

require 'openai'

def generate_docs(controller_file)
  code = File.read(controller_file)
  
  prompt = <<~PROMPT
    Analyze this Rails controller and generate API documentation.
    Include: endpoint URLs, HTTP methods, parameters, responses.
    
    Controller code:
    #{code}
  PROMPT

  client = OpenAI::Client.new(access_token: ENV['OPENAI_API_KEY'])
  response = client.chat(
    parameters: {
      model: "gpt-4",
      messages: [{ role: "user", content: prompt }]
    }
  )

  response.dig("choices", 0, "message", "content")
end

Engineers tried it. It worked. Suddenly, AI wasn't theoretical—it was saving them time.

Strategy 3: Make It Easy to Experiment

We created an internal AI Playground—a web interface where engineers could test prompts without writing code.

Features:

  • Pre-built prompt templates for common tasks
  • Model comparison (GPT-4 vs GPT-3.5 vs Claude)
  • Cost calculator (shows API cost per request)
  • Save and share successful prompts

Within two weeks, 40 engineers had experimented with LLMs. They shared their successes in Slack. The momentum built organically.

Strategy 4: Address Fears Head-On

"Will AI replace us?" This question came up constantly.

I gave an honest answer: AI won't replace engineers. Engineers who use AI will replace engineers who don't.

Then I showed data:

  • Our MR Review Agent didn't reduce reviewer headcount—it freed reviewers to focus on architecture instead of syntax
  • Documentation tools didn't eliminate tech writers—they let writers focus on tutorials instead of API refs
  • Code generation helped juniors ramp up faster—seniors mentored more people

AI augmented us. It didn't replace us.

Strategy 5: Run Internal Workshops

We ran monthly AI workshops:

  • Month 1: Prompt engineering basics
  • Month 2: Building with OpenAI API
  • Month 3: RAG pipelines for document search
  • Month 4: Fine-tuning models for domain tasks

Each workshop was 2 hours: 30 min theory, 90 min hands-on coding.

The key: real projects, not toy examples. In Month 2, we built a Slack bot that answers DevOps questions using our internal docs.

Strategy 6: Celebrate Wins Publicly

Every time an AI tool shipped, we shared it company-wide:

  • Demo in all-hands meetings
  • Write-up in engineering blog
  • Shout-outs in Slack #engineering channel

Recognition motivated teams. Other teams saw success and wanted in.

Measuring Success

We tracked:

  • Tool adoption: % of engineers using AI tools monthly (started 15%, now 78%)
  • Time saved: Self-reported hours saved per week (avg 3.5 hours/engineer)
  • Satisfaction: Quarterly survey on AI tool usefulness (4.2/5 rating)
  • Experimentation: # of new AI experiments started (12 in Q1, 34 in Q2)

The numbers told the story: AI adoption was working.

What Didn't Work

Not everything succeeded:

  • Auto-commit messages: LLM-generated commit messages were too generic. Engineers prefer writing their own.
  • Test generation: Generated tests passed but didn't test meaningful behavior. False confidence.
  • Code refactoring suggestions: Too opinionated. Engineers felt micromanaged.

We killed these projects fast. Better to fail quickly than force adoption of something people don't want.

Advice for Other Leaders

If you're leading AI adoption:

  • Start with problems, not technology: Find pain points first, then apply AI
  • Ship small wins fast: Don't spend 6 months building the perfect tool. Ship something useful in week 1.
  • Make experimentation easy: Remove barriers. Provide tools, templates, and support.
  • Address fears directly: Don't ignore "will AI replace us?" Talk about it openly.
  • Celebrate successes: Public recognition drives more adoption
  • Kill bad ideas fast: Not every AI experiment should become a product

The Mindset Shift

The biggest change wasn't technical. It was cultural.

Six months ago, engineers saw AI as a threat or a toy. Now they see it as a tool—like Git, like their IDE, like any other productivity multiplier.

The question isn't "Should we use AI?" anymore. It's "What problem can AI help us solve next?"

"AI adoption isn't about the technology. It's about showing people how it makes their lives better."
