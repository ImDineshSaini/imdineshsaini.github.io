When I started the Engineering AI Hub at SBS, half the team was skeptical. "It's just autocomplete," they said. "It writes buggy code." "It'll replace us."

Six months later, we built tools that cut development effort by 30%. Engineers who doubted AI became our biggest advocates.

This guide covers two things. First, the strategies that turned skeptics into believers. Second, the hands-on steps to get started yourself — from your first API call to building a working AI app.

The Resistance Was Real

The first AI Hub meeting had 8 people. Five came out of obligation. The energy was flat.

I understood the pushback. Engineers had seen hype before. Every year, something is the "next big thing." Most fade into nothing.

LLMs (Large Language Models — AI systems trained on massive text data) felt different to me. But I couldn't just say "trust me." I needed to show results.

Strategy 1: Start With Pain Points

I didn't start with LLM theory. I asked one question: "What's annoying in your daily work?"

The answers came fast:

  • "Writing API documentation is tedious"
  • "Code reviews take forever for obvious stuff"
  • "Breaking down user stories into tasks is repetitive"
  • "Debugging error logs is time-consuming"

Those became our first AI projects.

Strategy 2: Build Something Useful in Week 1

We built our first tool in a week: an API documentation generator.

Point it at a Python file, and it generates markdown docs with endpoints, parameters, and example responses. Not perfect, but 80% of the work done automatically.

Python — API doc generator with OpenAI 
import openai
import os

def generate_docs(filepath):
    with open(filepath) as f:
        code = f.read()

    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[{
            "role": "user",
            "content": f"Analyse this code and generate API docs.\n"
                       f"Include: endpoints, HTTP methods, params, responses.\n\n"
                       f"{code}"
        }]
    )
    return response.choices[0].message.content

Engineers tried it. It worked. AI wasn't theoretical any more — it was saving them time.

That first win changed the conversation. People stopped asking "Does AI work?" and started asking "What else can it do?"

Your First API Call: It's Easier Than You Think

Want to try this yourself? You can make your first API (Application Programming Interface — a way for programs to talk to each other) call in under 5 minutes.

Step 1: Get an API key. Sign up at platform.openai.com or console.anthropic.com. Copy your key.

Step 2: Install the library. Run pip install openai in your terminal.

Step 3: Send a prompt. Here is the simplest possible call:

import openai

response = openai.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Explain APIs in one sentence."}]
)
print(response.choices[0].message.content)

That's it. Six lines. You just talked to an LLM from your own code.

Step 4: Add multi-shot examples. Multi-shot (also called few-shot) prompting means you give the model examples of what you want. This makes the output more consistent.

Python — Multi-shot prompt example 
import openai

response = openai.chat.completions.create(
    model="gpt-4",
    messages=[
        {"role": "system", "content": "Extract the product name and price from text."},
        {"role": "user", "content": "I bought the UltraWidget for $29.99"},
        {"role": "assistant", "content": "Product: UltraWidget, Price: $29.99"},
        {"role": "user", "content": "Got the MegaTool at $49"},
        {"role": "assistant", "content": "Product: MegaTool, Price: $49.00"},
        {"role": "user", "content": "Just ordered a CloudBox for $199.50"}
    ]
)
print(response.choices[0].message.content)

The model sees the pattern from your examples and follows it. No extra instructions needed.

Step 5: Get structured JSON output. JSON (JavaScript Object Notation) is a standard data format. You can ask the model to return JSON so your code can parse the result easily.

Python — Structured JSON output 
import openai

response = openai.chat.completions.create(
    model="gpt-4",
    messages=[
        {"role": "system", "content": "Extract info and return valid JSON only."},
        {"role": "user", "content": "The CloudBox costs $199.50 and ships in 3 days."}
    ],
    response_format={"type": "json_object"}
)
print(response.choices[0].message.content)

The response comes back as clean JSON you can use directly in your app. No string parsing required.

Try It Yourself — Your First Prompt
You are a helpful coding assistant.

I'm building a REST API for a bookshop. Give me:
1. Three endpoint names (e.g. /books, /authors)
2. The HTTP method for each (GET, POST, etc.)
3. A one-sentence description of what each does

Return the result as a markdown table.
Paste this into ChatGPT or Claude. Then change "bookshop" to your own project and see what you get.

Build a Simple AI App: Frontend → Backend → LLM

Once you can make API calls, the next step is building a real app. Most AI apps follow a simple 3-layer pattern.

3-Layer AI App Architecture

User (Frontend)
→
Backend (Flask / Express)
→
LLM API (OpenAI / Claude)
Response displayed
←
Backend formats result
←
LLM returns answer

Here's how it works:

  1. The user types a message in the frontend (a web page or chat UI).
  2. The frontend sends that message to your backend server.
  3. The backend adds a system prompt, calls the LLM API, and waits for a response.
  4. The backend formats the result and sends it back to the frontend.
  5. The frontend displays the answer to the user.

Here is a minimal Flask backend that does this:

Python — Flask backend for a chat AI app 
from flask import Flask, request, jsonify
import openai

app = Flask(__name__)

@app.route("/chat", methods=["POST"])
def chat():
    user_message = request.json["message"]

    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[
            {"role": "system", "content": "You are a helpful coding assistant."},
            {"role": "user", "content": user_message}
        ]
    )

    answer = response.choices[0].message.content
    return jsonify({"reply": answer})

What this teaches you:

  • Flow of intent — the user's question travels through three layers and comes back as an answer.
  • Request/response — your backend makes an HTTP request to the LLM and returns the response.
  • JSON formatting — data moves between layers as JSON objects.
  • System prompts — you control the AI's behaviour by setting a system message in the backend.

You don't need a fancy frontend. Even a simple HTML form that posts to /chat works. Start small, then improve.

Try It Yourself — System Prompt for a Chat App
System prompt:
You are a senior code reviewer. When given code, respond with:
1. A summary of what the code does (2 sentences max)
2. One thing done well
3. One suggestion for improvement
Keep your tone friendly and constructive.

User message:
def add(a, b):
    result = a + b
    print(result)
    return result
Paste the system prompt and user message into ChatGPT or Claude. Try changing the system prompt to get different review styles.

Strategy 3: Make It Easy to Experiment

We created an internal AI Playground — a web interface where engineers could test prompts without writing code.

Features we included:

  • Pre-built prompt templates for common tasks
  • Model comparison (GPT-4 vs Claude)
  • Cost calculator showing API cost per request
  • Save and share successful prompts

Within two weeks, 40 engineers had tried LLMs. They shared results in Slack. The momentum built on its own.

The key is removing barriers. If someone has to read docs for an hour before trying AI, they won't bother. Give them a one-click way to start.

Strategy 4: Address Fears Head-On

"Will AI replace us?" This question came up constantly.

I gave an honest answer: AI won't replace engineers. Engineers who use AI will replace engineers who don't.

Then I showed real data from our team:

  • Our MR Review Agent didn't reduce reviewer headcount — it freed reviewers to focus on architecture instead of syntax.
  • Doc tools didn't replace tech writers — they let writers focus on tutorials instead of API refs.
  • Code generation helped juniors ramp up faster — seniors mentored more people.

AI augmented us. It didn't replace us.

Strategy 5: Run Internal Workshops

We ran monthly workshops with a simple format: 30 minutes of theory, 90 minutes of hands-on coding.

  • Month 1: Prompt engineering basics
  • Month 2: Building with the OpenAI API
  • Month 3: RAG (Retrieval-Augmented Generation — giving AI answers based on your own documents) pipelines
  • Month 4: Fine-tuning models for domain-specific tasks

The key: real projects, not toy examples. In Month 2, we built a Slack bot that answers DevOps questions using our internal docs.

Measuring Success

We tracked four metrics:

  • Tool adoption: percentage of engineers using AI tools monthly (started at 15%, now 78%)
  • Time saved: self-reported hours saved per week (average 3.5 hours/engineer)
  • Satisfaction: quarterly survey on AI tool usefulness (4.2 out of 5)
  • Experimentation: number of new AI experiments started (12 in Q1, 34 in Q2)

The numbers told the story. AI adoption was working.

What Didn't Work

Not everything succeeded:

  • Auto-commit messages: LLM-generated commit messages were too generic. Engineers prefer writing their own.
  • Test generation: Generated tests passed but didn't test meaningful behaviour. It created false confidence.
  • Code refactoring suggestions: Too opinionated. Engineers felt micromanaged by an AI.

We killed these projects fast. Better to fail quickly than force adoption of something people don't want.

Advice for Other Leaders

If you're leading AI adoption in your team:

  • Start with problems, not technology. Find pain points first, then apply AI.
  • Ship small wins fast. Don't spend 6 months building the perfect tool. Ship something useful in week 1.
  • Make experimentation easy. Remove barriers. Provide tools, templates, and support.
  • Address fears directly. Don't ignore "will AI replace us?" Talk about it openly.
  • Celebrate successes. Public recognition drives more adoption.
  • Kill bad ideas fast. Not every AI experiment should become a product.

The Mindset Shift

The biggest change wasn't technical. It was cultural.

Six months ago, engineers saw AI as a threat or a toy. Now they see it as a tool — like Git, like their IDE, like any other productivity multiplier.

The question isn't "Should we use AI?" any more. It's "What problem can AI help us solve next?"

"AI adoption isn't about the technology. It's about showing people how it makes their lives better."
