AML Compliance Architecture: Building Detection Systems That Scale

When regulators fined our partner bank $12 million for inadequate AML controls, the board asked one question: "How do we fix this without drowning compliance teams in false positives?"

That question led us to rebuild the entire AML detection system. We moved from a rule-based system generating 10,000+ false alerts per month to a hybrid ML+rules architecture with a 92% alert precision rate.

Here's the architecture that passed regulatory audits and actually works in production.

The AML Detection Challenge

Anti-Money Laundering systems face a unique constraint: you must catch 100% of suspicious activity while minimizing false positives. Miss something and regulators fine you. Flag too much and your compliance team drowns in alerts.

Our original system had these problems:

  • Rule explosion: 450+ hardcoded rules trying to catch every pattern
  • False positive rate: 98%: Only 2% of alerts were actual suspicious activity
  • Alert fatigue: Compliance analysts spent 80% of time on false positives
  • Tuning nightmares: Adjusting one rule broke others, causing cascading effects
  • Regulatory gaps: New laundering patterns took months to detect

The breaking point: A money mule network moved $2.3M through 50 accounts over 3 months. Our system flagged nothing because transactions stayed just under threshold rules.

AML System Architecture: The Hybrid Approach

Modern AML systems need both rules and machine learning. Rules handle known patterns and regulatory requirements. ML catches novel patterns humans miss.

Rule Engine vs. ML Detection: When to Use Each

After 2 years running this system, here's what works:

Use Rule-Based Detection For:

  • Regulatory requirements: FinCEN explicitly requires certain rules (e.g., $10K+ cash transactions)
  • Known typologies: Well-understood laundering patterns documented by FATF
  • Explainability: Regulators want to see "why" something was flagged - rules are auditable
  • Threshold violations: Simple conditions like "3+ international wires in 24h"

Use ML Detection For:

  • Novel patterns: Catching behavior that doesn't match known rules
  • Behavioral profiling: Learning normal user behavior, flagging deviations
  • Complex networks: Graph algorithms detecting money mule rings
  • False positive reduction: ML can learn which alerts are noise vs. signal

Architecture Deep Dive: The Rule Engine

We use Drools (Red Hat Decision Manager) for rule execution. It's battle-tested in banking and handles complex rule logic.

Example Structuring Detection Rule:

rule "Detect Structuring - Multiple Sub-Threshold Deposits"
when
  $account : Account()
  $deposits : List(size >= 3) from collect(
    Transaction(
      accountId == $account.id,
      type == "DEPOSIT",
      amount < 10000,
      timestamp after[24h] now
    )
  )
  Number(doubleValue >= 25000) from accumulate(
    Transaction($amt : amount) from $deposits,
    sum($amt)
  )
then
  Alert alert = new Alert();
  alert.setType("STRUCTURING");
  alert.setRiskScore(75);
  alert.setAccountId($account.getId());
  alert.setDescription("Multiple deposits under $10K totaling $25K+ in 24h");
  insert(alert);
end

Why Drools over hardcoded logic:

  • Rules live in a database, not code - compliance can tune without deployments
  • Version control for rule changes (regulatory audit requirement)
  • Rules can be tested independently
  • Performance: Drools uses Rete algorithm for efficient rule matching

Architecture Deep Dive: ML-Based Detection

Our ML system uses multiple models for different detection patterns:

ML Model Architecture

1. Anomaly Detection (Isolation Forest)
Flags unusual transactions compared to user's baseline behavior
Features: transaction amount, frequency, time-of-day, merchant type
2. Network Analysis (Graph Neural Network)
Detects money mule networks and circular transaction patterns
Input: Transaction graph with accounts as nodes, transfers as edges
3. Risk Scoring (XGBoost Classifier)
Learns from historical SARs (Suspicious Activity Reports)
Output: Probability score (0-100) of suspicious activity

Training Data Strategy:

  • Labeled data: Historical SARs filed + confirmed false positives
  • Feature engineering: 200+ features (velocity metrics, network centrality, device fingerprints)
  • Imbalanced data handling: True suspicious activity is < 0.1% of transactions - use SMOTE for oversampling
  • Retraining cadence: Models retrained monthly with new SAR data

Example: Graph Neural Network for Network Detection

import torch
from torch_geometric.nn import GCNConv

class AMLGraphDetector(torch.nn.Module):
    def __init__(self, num_features, hidden_dim):
        super().__init__()
        self.conv1 = GCNConv(num_features, hidden_dim)
        self.conv2 = GCNConv(hidden_dim, hidden_dim)
        self.classifier = torch.nn.Linear(hidden_dim, 1)

    def forward(self, x, edge_index):
        # x: node features (account attributes)
        # edge_index: transaction graph edges

        x = self.conv1(x, edge_index).relu()
        x = self.conv2(x, edge_index).relu()
        return self.classifier(x).sigmoid()

# Features: account age, transaction velocity, KYC completeness
# Edges: transfers between accounts (weighted by amount)
# Output: risk score for each account in the network

The False Positive Problem: How We Reduced Alerts by 85%

Early mistake: We treated every rule violation equally. An alert is an alert, right?

Wrong. Context matters.

Our Alert Scoring System:

final_score = (rule_score * 0.4) + (ml_anomaly_score * 0.3) +
              (network_risk_score * 0.2) + (customer_risk_score * 0.1)

Alert Tiers:
- Critical (90-100): Immediate investigation, possible SAR filing
- High (70-89): Review within 24h
- Medium (50-69): Batch review weekly
- Low (< 50): Suppressed (logged for audit only)

Customer Risk Scoring (KYC-based):

  • High-risk customers: PEPs (Politically Exposed Persons), high-risk industries (MSBs, crypto exchanges)
  • Geographic risk: Customer location + transaction destinations
  • Behavioral history: Previous SARs, account age, verification completeness

This tiered approach reduced compliance workload by 85% while maintaining 100% SAR filing accuracy.

Lesson 1: Real-Time vs. Batch Processing Trade-offs

We run two detection pipelines:

Dual Pipeline Architecture

Real-Time Pipeline (Kafka Streams)
Blocks transactions > $50K to high-risk countries (30ms latency)
Rule-based only (simple conditions for speed)
Batch Pipeline (Spark, runs hourly)
Complex pattern detection (velocity checks, network analysis)
ML models + graph algorithms (too slow for real-time)

Why the split?

  • Real-time: Prevent egregious violations before they complete
  • Batch: Catch sophisticated patterns that require historical context

Trade-off: Sophisticated structuring attacks aren't blocked immediately (flagged within 1 hour for investigation).

Lesson 2: Explainability is Regulatory Requirement

Regulators demand to know why you flagged (or didn't flag) something. "The ML model said so" doesn't fly in audits.

Our Explainability Strategy:

  • SHAP values: For ML predictions, generate feature importance explanations
  • Rule provenance: Every alert shows which rules triggered
  • Audit trail: Store full transaction context, model version, feature values at prediction time
  • Human-readable summaries: Auto-generate investigation notes

Lesson 3: Integration with Watchlists

AML systems must screen against global sanctions lists. We check:

  • OFAC SDN List: US Office of Foreign Assets Control Specially Designated Nationals
  • UN Sanctions Lists: United Nations consolidated list
  • PEP Databases: Politically Exposed Persons (Dow Jones, World-Check)
  • Adverse Media: Negative news screening

Screening Architecture:

// Real-time screening on transaction initiation
async function screenTransaction(transaction) {
  const results = await Promise.all([
    ofacScreening.check(transaction.recipientName),
    unScreening.check(transaction.recipientCountry),
    pepScreening.check(transaction.senderId)
  ]);

  const matchScore = calculateFuzzyMatch(results);

  if (matchScore > 95) {
    return { status: 'BLOCKED', reason: 'SANCTIONS_MATCH' };
  } else if (matchScore > 80) {
    return { status: 'REVIEW', reason: 'POTENTIAL_MATCH' };
  }
  return { status: 'APPROVED' };
}

Fuzzy Matching Challenge: Name variations (e.g., "Mohammed" vs "Muhammad") cause false positives. We use Levenshtein distance + phonetic algorithms to reduce false matches.

Regulatory Compliance: FinCEN Requirements

FinCEN (Financial Crimes Enforcement Network) requires financial institutions to:

  1. Currency Transaction Reports (CTRs): Auto-file for cash transactions > $10,000
  2. Suspicious Activity Reports (SARs): File within 30 days of detecting suspicious activity
  3. Customer Due Diligence (CDD): Know Your Customer (KYC) data collection
  4. Transaction Monitoring: Continuous surveillance for unusual patterns
  5. Record Retention: Keep records for 5 years (we keep 7 for safety)

System Design: Data Retention and Audit Trail

Every action must be auditable. Regulators will ask: "Why didn't you flag this transaction from 3 years ago?"

Our Data Strategy:

  • Transaction data: Store raw transactions for 7 years (PostgreSQL for recent data, S3 for archives)
  • Alert history: Every alert, investigation note, and decision logged immutably
  • Model versions: Track which model version scored each transaction (for reproducibility)
  • Rule changes: Version control all rule modifications with approval workflow

Production Lessons Learned

1. Start with Rules, Add ML Gradually

We initially tried an ML-first approach. Regulators rejected it. Now we use rules for core compliance, ML for enhancement.

2. Invest in Tooling for Analysts

Compliance teams aren't data scientists. Build intuitive investigation tools with one-click access to transaction history, network visualizations, and customer profiles.

3. False Positives Will Always Exist

You can't reach 0% false positives without missing real threats. Our target: 90%+ precision (10% false positive rate). Regulators accept this trade-off.

4. Test with Red Team Scenarios

We run quarterly "penetration tests" where internal teams try to move money without triggering alerts. This exposes blind spots.

5. Privacy Regulations Matter

GDPR complicates AML. We anonymize data for ML training, store PII separately with access controls, and purge data after retention period.

The Results

After 18 months with the new system:

  • Alert volume: 10,000/month → 1,500/month (85% reduction)
  • Alert precision: 2% → 92% (46x improvement)
  • SAR filings: Increased by 40% (catching more real threats)
  • Compliance workload: 80% time on false positives → 20%
  • Regulatory audits: Passed 2 audits with zero findings

Most importantly: Zero fines since the new system went live.

Trade-offs We Accepted

  • Complexity: System requires data scientists, compliance experts, and ML engineers
  • Cost: ML infrastructure + data storage + tooling = $500K/year operating cost
  • Latency: Batch detection means some threats aren't caught immediately
  • Model drift: Money laundering tactics evolve - models need constant retraining
