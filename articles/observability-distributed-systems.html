Observability in Distributed Systems: Finding Needles in Haystacks

When a banking transaction fails across 7 microservices, good luck finding out why.

Logs are scattered across containers. Traces are incomplete. Metrics show something's wrong, but not what. And the user is angry because their $500 transfer disappeared.

In a monolith, debugging is straightforward: add a breakpoint, trace the call stack, read the logs. In distributed systems, it's like solving a mystery where clues are scattered across 20 different crime scenes.

After building observability for a banking platform handling millions of transactions, here's what actually helps debug production issues.

Monitoring vs. Observability: What's the Difference?

People confuse these terms. They're not the same.

Monitoring tells you something is wrong. Dashboards, alerts, metrics.

Observability tells you why it's wrong. You can ask arbitrary questions without predicting failure modes upfront.

Monitoring vs. Observability

Monitoring (Known Unknowns)
✓ CPU > 80% → Alert
✓ Error rate > 1% → Alert
✓ Response time > 500ms → Alert
Problem: You must predict failure modes in advance
Observability (Unknown Unknowns)
✓ Why is user 12345's payment failing?
✓ Which service is causing the slowdown?
✓ What changed between 2pm and 3pm?
Benefit: Ask questions you didn't anticipate

You need both. Monitoring tells you to investigate. Observability helps you investigate.

The Three Pillars of Observability

The industry settled on three core signals:

1. Metrics (What is happening?)

Time-series data: counters, gauges, histograms.

  • Request rate: 500 req/sec
  • Error rate: 2%
  • Latency: p95 = 300ms
  • CPU, memory, disk usage

Best for: Dashboards, alerts, high-level health

2. Logs (What happened?)

Structured events from application code.

{
  "timestamp": "2024-11-18T14:23:45Z",
  "level": "error",
  "service": "payment-service",
  "traceId": "abc123",
  "message": "Payment failed: insufficient funds",
  "userId": "user_456",
  "amount": 500
}

Best for: Debugging specific errors, auditing

3. Traces (How did it flow?)

Request flow across multiple services.

Gateway (50ms)
  → Auth Service (20ms)
  → Payment Service (200ms)
    → Account Service (80ms) ← SLOW
    → Fraud Service (30ms)
  → Notification Service (10ms)

Best for: Understanding latency, service dependencies

System Design: Building Distributed Tracing

Tracing is the hardest pillar to get right. Here's our architecture:

Distributed Tracing Architecture

1. Generate Trace ID
API Gateway creates unique trace ID for each request
2. Propagate Context
Every service forwards trace ID + span ID in HTTP headers
traceparent: 00-abc123-def456-01
3. Record Spans
Each service records its operation as a "span"
Span = start time, end time, service name, operation
4. Send to Collector
Services send spans to OpenTelemetry Collector (async)
5. Store & Visualize
Jaeger/Tempo stores traces, Jaeger UI visualizes them

Our tracing stack:

  • Instrumentation: OpenTelemetry SDKs (auto-instrumentation for Node.js, Java)
  • Collection: OpenTelemetry Collector (aggregates spans, samples, batches)
  • Storage: Jaeger (short-term) + Tempo (long-term, cheaper)
  • Visualization: Jaeger UI, Grafana

Lesson 1: Context Propagation is Critical

If a single service doesn't forward the trace ID, the entire trace breaks.

We learned this when traces randomly ended at the Payment Service. Turns out, we forgot to propagate headers in one HTTP client library.

Automatic propagation with OpenTelemetry:

// Node.js example
const { trace, context, propagation } = require('@opentelemetry/api');

// Outgoing HTTP request
const span = trace.getActiveSpan();
const headers = {};

// Inject trace context into headers
propagation.inject(context.active(), headers);

await fetch('http://account-service/balance', {
  headers: {
    ...headers,  // Contains traceparent header
    'Authorization': token
  }
});

// Incoming HTTP request
app.use((req, res, next) => {
  // Extract trace context from headers
  const ctx = propagation.extract(context.active(), req.headers);
  context.with(ctx, next);
});

Key points:

  • Use standard W3C Trace Context format (traceparent header)
  • Auto-instrumentation handles this for common frameworks
  • For custom clients (gRPC, message queues), propagate manually

Lesson 2: Structured Logging > Text Logs

Early on, we logged like this:

console.log('Payment failed for user 123 amount 500');

Problems:

  • Hard to parse programmatically
  • Can't filter by userId or amount
  • No trace ID to correlate with traces

Better: Structured JSON logs

logger.error({
  event: 'payment.failed',
  traceId: trace.getActiveSpan()?.spanContext().traceId,
  userId: '123',
  amount: 500,
  reason: 'insufficient_funds',
  accountId: 'acc_789'
});

Benefits:

  • Query logs like a database: userId:"123" AND event:"payment.failed"
  • Correlate logs with traces using traceId
  • Aggregate metrics from logs (count payment failures by reason)

Our logging standard:

  • Always include: timestamp, level, service, traceId, event
  • Use consistent field names across services (userId not user_id or uid)
  • Redact sensitive data (PII, tokens, passwords)
  • Log at appropriate levels (ERROR for failures, INFO for key events, DEBUG for troubleshooting)

Lesson 3: Sampling Saves Costs

We can't trace every request. At 50K req/sec, storing all traces would cost $50K/month.

Sampling strategies:

Trace Sampling Strategies

Strategy Description Use Case
Fixed Rate Sample 1% of all requests Low-traffic services
Error-Based Sample 100% of errors, 1% of success Focus on failures
Latency-Based Sample slow requests (> 1s), 1% of fast ones Debug performance
Adaptive Increase sampling during incidents Balance cost & visibility

Our configuration:

# OpenTelemetry Collector config
processors:
  probabilistic_sampler:
    # Sample 1% of traces by default
    sampling_percentage: 1

  tail_sampling:
    policies:
      # Always sample errors
      - name: error-policy
        type: status_code
        status_code: {status_codes: [ERROR]}

      # Sample slow requests
      - name: latency-policy
        type: latency
        latency: {threshold_ms: 1000}

      # Sample 1% of everything else
      - name: probabilistic-policy
        type: probabilistic
        probabilistic: {sampling_percentage: 1}

This gives us:

  • 100% visibility into errors
  • 100% visibility into slow requests
  • 1% sample of happy path (for volume analysis)
  • 90% cost reduction vs. tracing everything

System Design: Centralized Logging Architecture

With 20+ services, you can't SSH into containers and tail -f logs. You need centralized logging.

Centralized Logging Architecture

1. Services Emit Logs
Applications log to stdout (JSON format)
2. Log Shipper (Fluent Bit)
DaemonSet on each Kubernetes node collects logs
3. Log Aggregator (Kafka)
Buffer logs (handles traffic spikes)
4. Storage (Elasticsearch)
Index logs for fast search (30-day retention)
5. Visualization (Kibana)
Query, filter, visualize logs

Key decisions:

  • Log to stdout: Don't write to files (containers are ephemeral)
  • Structured JSON: Parse once at shipper, not every query
  • Kafka buffer: Prevents log loss during Elasticsearch outages
  • Retention policy: 30 days in hot storage, 1 year in S3 (compliance)

Lesson 4: Metrics for Alerts, Traces for Root Cause

Don't alert on traces. Alert on metrics.

Why?

  • Metrics are cheap (aggregate data)
  • Traces are expensive (detailed per-request data)
  • Alerts need to fire instantly (metrics are pre-aggregated)

Our workflow:

Incident Response Workflow

1. Alert (Metrics)
Prometheus alert: "payment-service error rate > 1%"
2. Investigate (Logs)
Kibana: Filter logs by service, time range, error level
3. Deep Dive (Traces)
Copy traceId from logs → Jaeger → See full request flow
4. Root Cause
Trace shows Account Service timing out → Check its metrics/logs

Example alert:

# Prometheus alerting rule
- alert: HighErrorRate
  expr: |
    sum(rate(http_requests_total{status=~"5.."}[5m])) by (service)
    /
    sum(rate(http_requests_total[5m])) by (service)
    > 0.01
  for: 5m
  annotations:
    summary: "{{ $labels.service }} error rate > 1%"
    runbook: "Check Kibana for errors, then Jaeger for traces"

Lesson 5: Correlation IDs Tie Everything Together

The magic that connects metrics, logs, and traces: correlation IDs.

IDs we track:

  • Trace ID: Links all operations in a single request
  • Span ID: Identifies a specific operation within a trace
  • User ID: Links all requests from a user
  • Session ID: Links requests in a user session
  • Request ID: API gateway's unique ID (for support tickets)

Example correlation:

// User reports: "My payment failed, request ID req_xyz"

1. Kibana: Search requestId:"req_xyz"
   → Found log: traceId = "abc123", error = "timeout"

2. Jaeger: Search traceId:"abc123"
   → Trace shows: Account Service took 30s (should be <1s)

3. Prometheus: Check account-service latency at that timestamp
   → Latency spiked due to database connection pool exhaustion

4. Root cause: Database connection leak in recent deploy

Without correlation IDs, this investigation would take hours (or be impossible).

Lesson 6: Don't Over-Instrument

Early on, we instrumented everything. Every function call, every database query, every Redis get.

Result: 100K spans per trace. Jaeger UI was unusable. Storage costs exploded.

What to instrument:

  • ✅ HTTP requests (inbound and outbound)
  • ✅ Database queries
  • ✅ External API calls
  • ✅ Message queue operations
  • ✅ Critical business operations (payment processing, fraud checks)
  • ❌ Internal function calls
  • ❌ Logging operations
  • ❌ Metrics collection

Our rule: Instrument at service boundaries, not internal logic.

Real-World Debugging Story

A user reported: "I transferred $500, but it's not showing in my account."

Investigation:

  1. Kibana: Search userId + timestamp → Found: "Payment completed" log with traceId
  2. Jaeger: Trace shows Payment Service returned 200 OK
  3. Deeper search: Logs show Account Service never received the event
  4. Kafka lag: Check Kafka consumer lag → Payment events backed up 2 hours
  5. Root cause: Account Service consumer pod crashed (OOM), events queued in Kafka

Resolution:

  • Restarted Account Service consumer
  • Events processed from Kafka backlog
  • User's balance updated (2 hours late, but correct)
  • Added alert: "Kafka consumer lag > 5 minutes"

Without observability, we would have told the user "the payment failed" and asked them to retry (creating a duplicate payment).

Key Takeaways

  1. Observability ≠ Monitoring: Monitoring alerts, observability debugs.
  2. Correlation IDs are mandatory: Tie logs, metrics, and traces together.
  3. Structured logging: JSON logs with consistent field names.
  4. Distributed tracing: Propagate trace context across all services.
  5. Sampling: Trace errors and slow requests, sample happy path.
  6. Instrument at boundaries: HTTP, database, queues (not internal functions).
  7. Metrics → Logs → Traces: Use each tool for its strength.
