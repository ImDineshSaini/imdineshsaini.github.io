API Gateway Patterns: The Front Door to Your Microservices

Once you break a monolith into microservices, you face a new problem: how do clients talk to 20+ services?

Do mobile apps call each service directly? How do you handle authentication across services? What about rate limiting, logging, and monitoring?

Enter the API Gateway: the bouncer at the front door of your microservices architecture.

After building and scaling API gateways for a banking platform handling millions of transactions, here's what actually works.

The Problem: Direct Client-to-Service Communication

When we first migrated to microservices, we naively exposed services directly to clients:

Direct Access (Bad Pattern)

Mobile App
→ accounts.api.example.com
→ payments.api.example.com
→ notifications.api.example.com
→ fraud.api.example.com
Problems
❌ Client knows about internal services
❌ Each service handles auth independently
❌ No centralized rate limiting
❌ Can't change service URLs without breaking clients

This created chaos:

  • Chatty clients: Mobile app made 15 API calls to render a single screen
  • Authentication nightmare: Every service reimplemented JWT validation
  • No visibility: Logging and monitoring scattered across services
  • Security risks: Internal services directly exposed to the internet
  • Versioning hell: Breaking changes required coordinated client updates

What is an API Gateway?

An API Gateway is a reverse proxy that sits between clients and your microservices. It's the single entry point for all client requests.

API Gateway Architecture

Clients
Mobile App | Web App | Partner APIs
API Gateway (gateway.api.example.com)
Authentication | Rate Limiting | Request Routing | Response Transformation
Internal Services
Account Service | Payment Service | Notification Service | Fraud Service

Key responsibilities:

  • Request Routing: /api/accounts → Account Service
  • Authentication & Authorization: Validate JWT, enforce permissions
  • Rate Limiting: Prevent abuse (1000 req/min per user)
  • Load Balancing: Distribute traffic across service instances
  • Response Aggregation: Combine multiple service calls into one
  • Protocol Translation: HTTP → gRPC, REST → GraphQL
  • Observability: Centralized logging, metrics, tracing

Architecture Pattern 1: Simple Reverse Proxy

The simplest gateway pattern: route requests to services based on URL paths.

Configuration example (NGINX):

location /api/accounts {
  proxy_pass http://account-service:8080;
  proxy_set_header Authorization $http_authorization;
}

location /api/payments {
  proxy_pass http://payment-service:8080;
  proxy_set_header Authorization $http_authorization;
}

Pros: Simple, low latency, easy to understand
Cons: No business logic, limited transformation capabilities

Use when: You just need routing and don't need request/response transformation.

Architecture Pattern 2: Backend for Frontend (BFF)

Different clients (mobile, web, partners) have different needs. A BFF creates a custom gateway for each client type.

Backend for Frontend Pattern

Mobile BFF
Aggregates data, optimizes for 3G networks, returns minimal payloads
Web BFF
Returns richer data, supports browser-specific features
Partner API BFF
Enforces strict contracts, versioning, rate limits per partner
Backend Services
Shared microservices (Account, Payment, etc.)

Example: Mobile app needs account + recent transactions in one call.

// Mobile BFF endpoint
GET /mobile/dashboard

// Internally fetches:
1. Account Service: GET /accounts/123
2. Transaction Service: GET /transactions?accountId=123&limit=5

// Returns combined response:
{
  "account": { "balance": 1000 },
  "recentTransactions": [...]
}

Pros: Optimized per client, reduces round trips
Cons: More code to maintain, potential duplication

Use when: Clients have significantly different requirements (mobile vs. web vs. partners).

Architecture Pattern 3: GraphQL Gateway

Instead of REST endpoints, expose a GraphQL schema. Clients query exactly what they need.

query Dashboard {
  account(id: "123") {
    balance
    currency
    transactions(limit: 5) {
      id
      amount
      merchant
    }
  }
}

The GraphQL gateway federates queries across microservices.

Pros: Clients get exactly what they need, single endpoint
Cons: Complex gateway logic, N+1 query problems, caching challenges

Use when: You have diverse client needs and want flexibility. We use Apollo Federation for this.

System Design: Choosing a Gateway Technology

Not all gateways are built the same. Here's what we evaluated:

API Gateway Technology Comparison

Gateway Best For Trade-offs
NGINX Simple routing, high performance Limited business logic, config in files
Kong Feature-rich, plugin ecosystem Java-based (resource heavy), complex
AWS API Gateway Serverless, managed service AWS lock-in, limited customization
Envoy Proxy Service mesh, observability Complex config, steep learning curve
Traefik Kubernetes-native, auto-discovery Less mature, smaller community
Custom (Node.js/Go) Full control, business logic Build and maintain yourself

Our choice: We use Kong for external APIs (rich plugins for auth, rate limiting) and Envoy for internal service mesh (observability, traffic management).

Lesson 1: Avoid the Smart Gateway Trap

It's tempting to put business logic in the gateway. Don't.

Bad: Gateway validates payment limits, calculates fees, checks fraud rules.

Why it's bad:

  • Gateway becomes a monolith
  • Business logic duplicated (gateway + services)
  • Hard to test independently
  • Deployment bottleneck

Good: Gateway handles routing, auth, rate limiting. Services handle business logic.

Gateway responsibilities:

  • ✅ Authentication & authorization
  • ✅ Rate limiting & throttling
  • ✅ Request routing
  • ✅ Protocol translation (HTTP → gRPC)
  • ✅ Response aggregation (combine service calls)
  • ❌ Business validation (payment limits, fraud checks)
  • ❌ Data transformation beyond formatting
  • ❌ Database queries

Lesson 2: Rate Limiting Saves Your Backend

Without rate limiting, a misbehaving client can DDoS your services.

We learned this when a partner's buggy integration retried failed requests in a tight loop. 50,000 requests/second brought down our payment service.

Our rate limiting strategy:

Multi-Tier Rate Limiting

Global Rate Limit
100K requests/second (DDoS protection)
Per-Client Rate Limit
1K requests/minute per API key
Per-Endpoint Rate Limit
POST /payments: 10/min, GET /accounts: 100/min
Burst Protection
Token bucket algorithm allows short bursts

Implementation (using Kong):

curl -X POST http://kong:8001/services/payment-service/plugins \
  --data "name=rate-limiting" \
  --data "config.minute=1000" \
  --data "config.policy=redis" \
  --data "config.redis_host=redis.example.com"

Key decisions:

  • Use Redis for distributed rate limiting (shared state across gateway instances)
  • Return 429 Too Many Requests with Retry-After header
  • Different limits for free vs. paid tiers
  • Graceful degradation (rate limit non-critical endpoints first)

Lesson 3: Authentication at the Gateway, Authorization at the Service

There's a crucial distinction between authentication (who are you?) and authorization (what can you do?).

Our pattern:

Auth Flow

1. Gateway: Authentication
Validate JWT signature, check expiration, extract user ID
2. Gateway: Pass user context
Add headers: X-User-ID, X-User-Roles
3. Service: Authorization
Check if user can access this specific resource
Example: Can user 123 transfer from account 456?

Why this separation?

  • Gateway doesn't know business rules ("Can this user transfer $10K?")
  • Services have full context (account ownership, transaction limits)
  • Gateway ensures valid tokens, services enforce policies

Example:

// Gateway validates JWT
if (!jwt.verify(token, publicKey)) {
  return 401 Unauthorized
}

// Gateway adds user context
req.headers['X-User-ID'] = jwt.userId
req.headers['X-User-Roles'] = jwt.roles

// Service checks authorization
if (account.ownerId !== req.headers['X-User-ID']) {
  return 403 Forbidden
}

Lesson 4: Circuit Breakers Prevent Cascading Failures

When a backend service goes down, the gateway shouldn't retry blindly and make things worse.

Circuit Breaker Pattern:

Circuit Breaker States

Closed (Normal)
Requests pass through. Track failures.
Open (Service Down)
After 5 failures in 10s, stop sending requests. Return 503 immediately.
Half-Open (Testing)
After 30s, allow 1 test request. If succeeds, close circuit. If fails, open again.

Using Envoy's circuit breaker:

circuit_breakers:
  thresholds:
    - priority: DEFAULT
      max_connections: 1000
      max_pending_requests: 1000
      max_requests: 1000
      max_retries: 3
outlier_detection:
  consecutive_5xx: 5
  interval: 10s
  base_ejection_time: 30s

This prevents the gateway from overwhelming a struggling service with retries.

System Design: Handling High Traffic

Our gateway handles 50K+ requests/second. Here's how we scaled:

1. Horizontal Scaling

  • Run multiple gateway instances (10+ pods in Kubernetes)
  • Load balancer distributes traffic (AWS ALB)
  • Stateless design (no sticky sessions)

2. Connection Pooling

  • Reuse HTTP connections to backend services
  • Pool size: 100 connections per service
  • Reduces handshake overhead (TCP + TLS)

3. Response Caching

  • Cache idempotent GET requests (user profile, account info)
  • Use Redis with short TTL (30 seconds)
  • Reduces backend load by 40%

4. Request Deduplication

  • If 100 clients request the same data simultaneously, only send 1 backend request
  • Return cached response to all 100 clients
// Request coalescing pseudocode
const inFlightRequests = new Map();

async function fetchAccount(accountId) {
  if (inFlightRequests.has(accountId)) {
    // Wait for existing request
    return inFlightRequests.get(accountId);
  }

  const promise = accountService.fetch(accountId);
  inFlightRequests.set(accountId, promise);

  try {
    return await promise;
  } finally {
    inFlightRequests.delete(accountId);
  }
}

Monitoring & Observability

The gateway is your observability goldmine. Every request flows through it.

Metrics we track:

  • Request rate: req/sec per endpoint, per client
  • Latency: p50, p95, p99 response times
  • Error rates: 4xx (client errors), 5xx (server errors)
  • Rate limit hits: Track when clients are throttled
  • Circuit breaker state: Alert when circuits open

Tracing:

  • Every request gets a unique trace ID
  • Propagate trace ID to all downstream services
  • Use OpenTelemetry + Jaeger for distributed tracing

Logging:

{
  "traceId": "abc123",
  "method": "POST",
  "path": "/api/payments",
  "userId": "user_456",
  "clientIp": "192.168.1.1",
  "statusCode": 200,
  "latency": 45,
  "backend": "payment-service",
  "timestamp": "2025-04-12T10:30:00Z"
}

We ship logs to Elasticsearch and visualize in Kibana.

Security Best Practices

1. TLS Everywhere

  • Client → Gateway: TLS 1.3
  • Gateway → Services: mTLS (mutual TLS)
  • Terminate TLS at the gateway (offload from services)

2. Input Validation

  • Max request size: 1MB (prevent payload bombs)
  • Validate content-type headers
  • Sanitize inputs (prevent injection attacks)

3. API Key Management

  • Hash API keys (never store plaintext)
  • Support key rotation without downtime
  • Allow key revocation instantly

4. DDoS Protection

  • Use AWS Shield for L3/L4 protection
  • Gateway rate limiting for L7 protection
  • Challenge suspicious traffic (CAPTCHA)

The Results

After implementing a proper API gateway:

  • Simplified clients: Mobile app went from 15 endpoints to 1 gateway
  • Faster iteration: Backend services change without breaking clients
  • Better security: Centralized auth, rate limiting, TLS termination
  • Improved observability: Single place to track all API traffic
  • Cost savings: Response caching reduced backend load by 40%

Key Takeaways

  1. Gateway is for routing, not business logic: Keep it thin.
  2. Rate limiting is mandatory: Protect your backend from bad clients.
  3. Use circuit breakers: Prevent cascading failures.
  4. BFF pattern for diverse clients: Optimize for mobile, web, partners separately.
  5. Authentication at gateway, authorization at service: Proper separation of concerns.
  6. Observability is critical: Gateway is your central monitoring point.
