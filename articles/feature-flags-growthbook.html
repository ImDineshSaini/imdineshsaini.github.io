Feature Flags with GrowthBook: Deploy Fearlessly

We deployed a new payment flow on Friday afternoon. By 5pm, we realized it had a critical bug.

In the old days, this meant: revert the deploy, fix the bug, redeploy, hope nothing else broke. 2-3 hours of stress.

With feature flags? We toggled the flag off in 30 seconds. Users instantly fell back to the old flow. We fixed the bug Monday morning and toggled the flag back on.

No deploy. No rollback. No outage.

After implementing feature flags with GrowthBook across our banking platform, here's what actually works.

What Are Feature Flags?

Feature flags (aka feature toggles) are if statements controlled from outside your code.

// Without feature flag
function processPayment(payment) {
  return newPaymentFlow(payment);
}

// With feature flag
function processPayment(payment) {
  if (featureFlags.isEnabled('new-payment-flow')) {
    return newPaymentFlow(payment);
  } else {
    return oldPaymentFlow(payment);
  }
}

The magic: You can toggle the flag without deploying code.

Why Feature Flags Changed Everything

Before feature flags, we faced a dilemma:

  • Merge incomplete work? Risk breaking production.
  • Keep feature branches? Merge conflicts, integration hell.

With feature flags, we ship incomplete features to production hidden behind flags. Then we:

  • Test in production with real data
  • Roll out gradually (5% → 25% → 50% → 100%)
  • A/B test different implementations
  • Kill switch bad deploys instantly

Deployment Strategy Evolution

Traditional: All-or-Nothing
Deploy → Hope it works → Rollback if it doesn't (downtime)
With Feature Flags: Gradual Rollout
Deploy (flag off) → Enable 5% → Monitor → Enable 100% (no downtime)

Feature Flag Patterns

Not all flags are the same. Here are the patterns we use:

1. Release Flags (Temporary)

Purpose: Hide incomplete features in production

Lifetime: Days to weeks (delete after full rollout)

if (flags.isEnabled('new-dashboard-ui')) {
  return ;
} else {
  return ;
}

// After 100% rollout: Delete flag, delete old code

2. Ops Flags (Long-Lived)

Purpose: Operational control (rate limiting, maintenance mode)

Lifetime: Permanent

if (flags.isEnabled('maintenance-mode')) {
  return 503 Service Unavailable;
}

if (flags.isEnabled('enable-rate-limiting')) {
  applyRateLimit(user);
}

3. Experiment Flags (A/B Testing)

Purpose: Compare multiple implementations

Lifetime: Until experiment concludes

const variant = flags.getVariant('checkout-button-color');
// variant = 'blue' | 'green' | 'red'

return ;

// Track conversion rates, pick winner

4. Permission Flags (Entitlement)

Purpose: Enable features for specific users/tiers

Lifetime: Permanent

if (flags.isEnabled('advanced-analytics', { userId })) {
  return ;
} else {
  return ;
}

Architecture: How GrowthBook Works

GrowthBook Architecture

1. GrowthBook Admin UI
Product managers create/edit flags, set targeting rules
2. GrowthBook API
Generates JSON payload with all flag definitions
3. CDN (Optional)
Cache JSON payload for ultra-low latency (~10ms)
4. Application SDK
Fetches payload, evaluates flags locally (no API calls per request)

Key insight: GrowthBook SDKs evaluate flags locally (client-side or server-side). No network call per feature check = fast.

Implementation: GrowthBook in Node.js

1. Install SDK:

npm install @growthbook/growthbook

2. Initialize GrowthBook:

const { GrowthBook } = require('@growthbook/growthbook');

const gb = new GrowthBook({
  apiHost: "https://cdn.growthbook.io",
  clientKey: "sdk-abc123",
  enableDevMode: process.env.NODE_ENV === 'development',

  // Set user attributes for targeting
  attributes: {
    id: user.id,
    email: user.email,
    country: user.country,
    plan: user.subscriptionPlan,
    signupDate: user.createdAt
  }
});

// Fetch feature definitions
await gb.loadFeatures();

3. Check feature flags:

// Boolean flag
if (gb.isOn('new-payment-flow')) {
  processNewPayment();
} else {
  processOldPayment();
}

// Get variant (A/B test)
const buttonColor = gb.getFeatureValue('checkout-button-color', 'blue');

// Get complex feature value
const config = gb.getFeatureValue('payment-config', {
  maxAmount: 1000,
  allowedCountries: ['US', 'CA']
});

4. Track experiment exposure:

// Automatically track when user sees an experiment
gb.setTrackingCallback((experiment, result) => {
  analytics.track('Experiment Viewed', {
    experimentId: experiment.key,
    variationId: result.variationId,
    userId: user.id
  });
});

Lesson 1: Start Simple, Avoid Over-Engineering

Early mistake: We created flags for everything. 200+ flags within 3 months.

Problems:

  • Nobody knew which flags were active
  • Old flags lingered (technical debt)
  • Code became unreadable (nested if statements)

Our new rules:

  1. Default to no flag: Only add flags for risky changes
  2. Naming convention: release/new-payment-flow, ops/maintenance-mode, exp/checkout-button-color
  3. Expiration dates: Release flags auto-archive after 30 days
  4. Delete after rollout: When flag reaches 100%, remove code + flag

Lesson 2: Targeting Rules Are Powerful

GrowthBook lets you enable features for specific users/segments without code changes.

Example targeting rules:

// Enable for internal team only
if (user.email.endsWith('@company.com')) {
  enabled = true;
}

// Enable for 10% of users (gradual rollout)
if (hash(user.id + flagKey) % 100 < 10) {
  enabled = true;
}

// Enable for premium users in US
if (user.plan === 'premium' && user.country === 'US') {
  enabled = true;
}

This lets product managers control rollouts without engineering involvement.

Lesson 3: Feature Flags ≠ Technical Debt (If Managed)

Flags become debt when you forget to remove them.

Our flag lifecycle:

Feature Flag Lifecycle

1. Creation
Engineer creates flag, sets expiration (30 days)
2. Gradual Rollout
0% → 5% → 25% → 50% → 100% over 2 weeks
3. Stabilization
Run at 100% for 1 week, monitor metrics
4. Cleanup
Remove flag from code, delete old implementation

Automated cleanup:

  • Weekly Slack reminder: "5 flags expire this week"
  • CI fails if flag older than 90 days (forces cleanup)
  • GrowthBook archives unused flags automatically

System Design: Edge-Based Flag Evaluation

For low-latency flag checks, we evaluate at the CDN edge (Cloudflare Workers).

Edge Flag Evaluation

Traditional (Slow)
User → Server → GrowthBook API → Server → User (200ms)
Edge-Based (Fast)
User → Cloudflare Worker (evaluates flags locally) → Server (10ms)

Cloudflare Worker example:

import { GrowthBook } from '@growthbook/growthbook';

export default {
  async fetch(request, env) {
    const gb = new GrowthBook({
      attributes: {
        id: request.headers.get('X-User-ID'),
        country: request.cf.country
      },
      features: JSON.parse(await env.KV.get('growthbook-features'))
    });

    if (gb.isOn('new-payment-flow')) {
      return fetch('https://api.example.com/v2/payment', request);
    } else {
      return fetch('https://api.example.com/v1/payment', request);
    }
  }
};

GrowthBook's feature JSON is cached in Cloudflare KV (edge storage), so evaluation is nearly instant.

Week 1: Internal testing

// Enable for employees only

  enabled = true;

Week 2: Beta users (5%)

// Gradual rollout to 5% of users
if (hash(user.id) % 100 < 5) {

Monitoring & Observability

Track these metrics:

  • Flag evaluation latency: Should be <10ms (local evaluation)
  • Feature payload fetch time: How long to load flag definitions
  • Flag usage: Which flags are checked most often
  • Stale flags: Flags older than 90 days (technical debt)

GrowthBook provides analytics:

  • Experiment results (conversion rates, confidence)
  • Feature usage (how many users see each variant)
  • SDK performance metrics

Security Considerations

1. Client-side vs Server-side flags

  • Client-side (JS/mobile): Users can see flag values (inspect network). Only use for UI changes.
  • Server-side (Node/Python): Secure. Use for sensitive features (payment flows, admin access).

2. Encrypt sensitive flag payloads

If flags contain sensitive config (API keys, feature limits), encrypt the payload.

3. Audit flag changes

GrowthBook logs who changed flags and when. Critical for compliance.

The Results

After 18 months with feature flags:

  • Deploy frequency: 5/day → 20/day (trunk-based development)
  • Rollback rate: 15% → 2% (flags instead of rollbacks)
  • Mean time to recovery: 45 min → 2 min (toggle flag off)
  • A/B tests run: 0 → 30+ experiments/quarter
  • Production incidents: Down 60% (safer deployments)

Key Takeaways

  1. Feature flags enable trunk-based development: Ship incomplete work safely.
  2. Gradual rollouts reduce risk: 5% → 100% over days, not all-or-nothing.
  3. Kill switches save incidents: Toggle off bad features in seconds.
  4. A/B testing drives decisions: Data beats opinions.
  5. Clean up old flags: Set expiration dates, automate reminders.
  6. GrowthBook is great for startups/mid-market: Open source, affordable, A/B testing built-in.
