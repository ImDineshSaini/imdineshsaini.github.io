Trunk-Based Development: Why We Ditched Long-Lived Feature Branches

For years, our team followed Git Flow religiously. Feature branches lived for weeks. Merge conflicts were daily battles. Releases were stressful coordination exercises.

Then we switched to trunk-based development. Everyone commits to main. Branches live hours, not weeks. Releases happen 20+ times per day.

It felt scary at first. Now we can't imagine going back.

The Problem With Long-Lived Branches

Git Flow made sense in 2010. It doesn't in 2025.

Here's what we experienced with long-lived feature branches:

  • Merge hell: Feature branches diverged from main for 2-3 weeks. Merging back was painful.
  • Integration surprises: Features worked in isolation but broke when combined.
  • Deployment delays: Finished features waited for the next release window.
  • Code review bottlenecks: Reviewing 2 weeks of changes took hours.

The final straw: A critical security patch took 4 days to deploy because we had to wait for unrelated features to finish testing on the release branch.

That's when we explored trunk-based development.

What Is Trunk-Based Development?

The concept is simple: everyone commits directly to the main branch (trunk). No long-lived feature branches.

Git Flow vs Trunk-Based Development

Git Flow
main → develop → feature branches (weeks) → release branch → main
Trunk-Based
main ← short-lived branches (hours) → main continuously

Rules we follow:

  • Branches must merge within 24 hours (ideally < 4 hours)
  • Main branch is always deployable
  • Feature flags control incomplete features
  • CI/CD runs on every commit to main
  • Automated tests catch regressions immediately

Lesson 1: Small, Frequent Commits

The key to trunk-based development: commit small changes often.

Instead of completing an entire feature before merging, we break work into tiny increments:

  • Add database migration → commit
  • Create model class → commit
  • Add API endpoint (behind feature flag) → commit
  • Write tests → commit
  • Add UI (hidden by flag) → commit
  • Enable feature flag → commit

Each commit is small, reviewable, and independently deployable.

Lesson 2: Feature Flags Are Essential

You can't deploy incomplete features to production without feature flags.

We use feature flags to hide work-in-progress:

if FeatureFlag.enabled?(:new_kyc_flow, user: current_user)
  render 'kyc/new_flow'
else
  render 'kyc/legacy_flow'
end

This lets us:

  • Deploy incomplete features to production (disabled by default)
  • Test in production with a small % of users
  • Rollback instantly by toggling a flag (no redeployment needed)
  • Gradual rollouts (5% → 25% → 50% → 100%)

Tools We Use:

  • LaunchDarkly: Enterprise feature flag platform - https://launchdarkly.com/
  • GrowthBook: Open-source A/B testing + feature flags - https://www.growthbook.io/
  • Unleash: Self-hosted feature toggles - https://www.getunleash.io/

Lesson 3: CI/CD Must Be Fast

Trunk-based development requires fast CI/CD. If tests take 30 minutes, nobody will commit frequently.

We optimized our pipeline:

  • Parallel test execution: Split test suite across 10 workers
  • Selective testing: Only run tests affected by code changes
  • Docker layer caching: Skip rebuilding unchanged dependencies
  • Fast feedback loop: Unit tests run in < 2 min, full suite in < 8 min

Pipeline went from 28 minutes to 8 minutes. Commit frequency doubled.

CI/CD Tools:

  • GitHub Actions: https://github.com/features/actions
  • GitLab CI/CD: https://docs.gitlab.com/ee/ci/
  • CircleCI: https://circleci.com/

Lesson 4: Code Review Shifts Left

Small commits = faster code reviews.

Before trunk-based: "Review my 47-file, 2000-line feature branch."

After trunk-based: "Review my 3-file, 80-line commit."

Reviews that took hours now take 10 minutes. Feedback is immediate, not days later.

We also pair program more often. When two people write code together, formal review becomes less critical.

Lesson 5: Main Branch Protection

Since main is always deployable, we enforce quality gates:

  • ✅ All tests must pass
  • ✅ Code coverage must not decrease
  • ✅ At least 1 approval required for merge
  • ✅ No merge conflicts
  • ✅ Security scans must pass (no high/critical vulnerabilities)

GitHub/GitLab branch protection rules enforce these automatically.

Branch Protection Setup:

# .github/workflows/branch-protection.yml
name: Branch Protection
on:
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Run Tests
        run: bundle exec rspec
      - name: Check Coverage
        run: bundle exec rake coverage:check
      - name: Security Scan
        run: bundle exec brakeman --no-pager

The Migration Process

We didn't flip a switch. We migrated gradually:

Migration to Trunk-Based Development

Month 1: Training
→
Month 2: Pilot Team
→
Month 3: Add Feature Flags
→
Month 4: Full Adoption

Month 1: Team training on trunk-based principles and feature flags

Month 2: One team pilots trunk-based dev, reports learnings

Month 3: Deploy feature flag system, integrate into codebase

Month 4: All teams switch to trunk-based, retire Git Flow branches

What We Gained

After 6 months of trunk-based development:

  • Deployment frequency: 4/week → 20+/day
  • Lead time: Code to production in < 4 hours (was 2-3 weeks)
  • Merge conflicts: Down 90% (small, frequent merges reduce conflicts)
  • Failed deployments: Down 60% (smaller changes = less risk)
  • Hotfix time: Critical fixes deploy in < 30 min (no waiting for releases)

The biggest win: psychological safety. Engineers ship changes confidently knowing they can rollback with a feature flag toggle.

What About Releases?

We don't do "releases" anymore in the traditional sense. Main is always production-ready.

We use feature flags for rollouts:

  • Enable for internal users first (dogfooding)
  • Gradual rollout: 5% → 25% → 50% → 100%
  • Monitor metrics at each stage
  • Rollback if issues detected (toggle flag off)

This is safer than big-bang releases.

Common Objections

"What if someone breaks main?"

It happens. When it does, we revert the commit immediately. Because commits are small, reverts are safe. In 6 months, we've reverted 8 commits. Total downtime: < 15 minutes combined.

"What about unfinished features?"

Feature flags. Deploy code disabled, enable when ready.

"Our tests are slow."

Fix them. Slow tests are a blocker regardless of branching strategy. Invest in parallelization and selective testing.

When Trunk-Based Development Doesn't Fit

Trunk-based isn't for everyone:

  • Open-source projects with external contributors (Git Flow works better)
  • Teams without strong CI/CD (fix that first)
  • Regulated industries where every deploy needs approval (use release trains instead)

For product teams building web services, trunk-based is transformative.

"Trunk-based development isn't about abandoning branches. It's about keeping them short-lived."
