Building AI Agents That Actually Help: Lessons from the Trenches

It started with a simple observation: our engineering team was spending hours every week reviewing merge requests. Not because the code was bad, but because someone had to check if tests were written, documentation was updated, and coding standards were followed. The repetitive stuff.

"What if an AI could do the first pass?" someone suggested during a retrospective.

That conversation turned into a weekend experiment. The weekend experiment became a prototype. And six months later, our MR Review Agent had reviewed over 2,000 merge requests and reduced initial review time by 30%.

Here's the story of what we learned building AI agents that don't just impress in demos, but actually ship value in production.

The Problem: Code Review Bottlenecks

Every engineering team hits the same wall: as you grow, code review becomes a bottleneck. Senior engineers spend hours reviewing instead of building. Junior engineers wait days for feedback. Merge requests pile up.

We tried the usual solutions — better PR templates, review checklists, rotation schedules. They helped, but didn't solve the core issue: reviewing code is mentally exhausting.

Not because it's hard to spot bugs (though it can be), but because 80% of review feedback is about the same things: "Where are the tests?" "Did you update the README?" "This variable name isn't descriptive."

That's when we realized: the repetitive stuff is exactly what LLMs are good at.

Building the First Version: Simpler Than You Think

The first prototype was embarrassingly simple. We used the GitLab API to fetch merge request diffs, sent them to GPT-4 with a detailed system prompt, and posted the response as a comment. The whole thing was maybe 200 lines of Python.

The system prompt was key. We didn't ask the LLM to review "code quality" (too vague). Instead, we gave it a checklist:

  • Are there unit tests for new functionality?
  • Is error handling present for external calls?
  • Are variable names descriptive and follow conventions?
  • Is documentation updated if APIs changed?
  • Are there any obvious security issues (SQL injection, XSS, hardcoded secrets)?

Specificity made all the difference. Vague prompts produce vague reviews. Specific checklists produce actionable feedback.

Lesson 1: Start With Narrow Scope

The temptation with AI is to solve everything at once. "Let's build an agent that reviews code AND suggests refactors AND finds bugs AND writes documentation!"

We almost fell into that trap. Thankfully, we didn't.

Instead, we focused on one thing: catching missing tests and documentation. That's it. No architectural advice, no performance optimization suggestions, just the basics.

Why? Because when the agent inevitably got something wrong (and it did), the blast radius was small. A false positive about missing tests is annoying. A false positive about "rewriting your entire API" is dangerous.

Start narrow. Expand later.

Lesson 2: Humans Are Still in the Loop

Here's something we got right from day one: the agent never blocks a merge.

It posts comments. That's all. Engineers can read them, ignore them, or engage with them. It never changes code, never rejects PRs, never auto-merges anything.

This was crucial for adoption. If the agent could block work, engineers would find ways to disable it. If it could modify code, engineers would lose trust. But as a helpful assistant that posts suggestions? People loved it.

One engineer told me: "It's like having a junior reviewer who never gets tired and always remembers to check the basics."

Lesson 3: Context is Everything

Early versions of our agent would sometimes suggest adding tests for test files. Or complain about missing documentation in configuration files. Technically correct input, absurd output.

The problem? Lack of context.

We fixed this by giving the agent more information:

  • File paths (test files vs source files vs config files)
  • Git history (is this a refactor or new functionality?)
  • PR description (what is the author trying to accomplish?)
  • Project conventions (from a conventions.md file we created)

With better context, the reviews got dramatically better. It stopped suggesting tests for tests and started making actually useful observations.

Lesson 4: Cost Matters

Our first month running the agent cost $847 in API calls. We were sending entire file diffs for every merge request, sometimes thousands of lines of code per review.

We optimized in three ways:

  • Smart chunking: Instead of sending entire files, we sent only changed sections plus a few lines of context.
  • Caching: Repeated reviews of the same MR reused previous analysis.
  • Model selection: We use GPT-4 for complex reviews, but GPT-3.5-turbo for simple checks like "are there tests?"

After optimization, monthly costs dropped to $180 while maintaining review quality. For a team of 30 engineers, that's $6 per person per month — a bargain compared to the time saved.

What's Next: Beyond Code Review

The MR Review Agent was our gateway drug into AI agents. Once we proved the concept worked, the team started imagining other uses:

We're now building an Agile Planning Agent that takes user stories and suggests technical subtasks. Early tests show it's particularly good at remembering edge cases humans forget ("What about mobile?", "Did we consider rate limiting?").

The Real Lesson: AI Agents Are Tools, Not Magic

After building agents for a year, here's my biggest takeaway: AI agents aren't replacing engineers. They're augmenting them.

The MR Review Agent doesn't replace human reviewers. It makes them more efficient. Instead of spending 30 minutes checking if tests exist and documentation is updated, reviewers now spend 30 minutes on the interesting stuff: architecture decisions, edge cases, and teaching moments.

The best AI agents are the ones that free humans to do what humans do best: think creatively, make judgment calls, and build relationships.

If you're building AI agents, don't try to replace your team. Build tools that make them superhuman instead.

"The best tools don't replace expertise. They amplify it."

Key Takeaways:

  • Start with narrow scope — solve one problem really well before expanding
  • Keep humans in the loop — agents should assist, not automate decisions
  • Context is crucial — the more context you give an LLM, the better its output
  • Cost matters — optimize for both quality and API spend
  • Focus on augmentation, not replacement — make humans superhuman
