It started with a simple observation. Our engineering team spent hours every week reviewing merge requests. The code wasn't bad. Someone just had to check if tests were written, docs were updated, and coding standards were followed. The repetitive stuff.

"What if an AI could do the first pass?" someone suggested during a retrospective.

That conversation turned into a weekend experiment. The experiment became a prototype. Six months later, our MR Review Agent had reviewed over 2,000 merge requests. It cut initial review time by 30%.

Here's what we learned building agents that work in the real world, not just in demos.

The Problem: Code Review Bottlenecks

Every engineering team hits the same wall. As you grow, code review becomes a bottleneck. Senior engineers spend hours reviewing instead of building. Junior engineers wait days for feedback.

We tried the usual fixes: better PR templates, review checklists, rotation schedules. They helped, but didn't solve the core issue. Reviewing code is mentally draining.

Not because spotting bugs is hard. It's because 80% of feedback covers the same things. "Where are the tests?" "Did you update the README?" "This variable name isn't clear enough."

That's when we realized: the repetitive stuff is exactly what LLMs are good at. LLMs (large language models) are AI systems trained on text that can read and reason about code.

Building the First Version: Simpler Than You Think

The first prototype was embarrassingly simple. We used the GitLab API to fetch merge request diffs. We sent them to GPT-4 with a detailed system prompt. Then we posted the response as a comment. The whole thing was about 200 lines of Python.

The system prompt was key. We didn't ask the LLM to review "code quality" — that's too vague. Instead, we gave it a specific checklist.

Python — GitLab webhook handler 
@app.post("/webhook/merge-request")
async def handle_mr(payload: dict):
    mr_id = payload["object_attributes"]["iid"]
    project_id = payload["project"]["id"]

    # Fetch the diff from GitLab API
    diff = gitlab.get_mr_diff(project_id, mr_id)

    # Send to LLM for review
    review = await review_agent.analyze(diff)

    # Post review as MR comment
    gitlab.post_comment(project_id, mr_id, review)
    return {"status": "ok"}

Here's what the system prompt checks for:

  • Are there unit tests for new functionality?
  • Is error handling present for external calls?
  • Are variable names descriptive and following conventions?
  • Is documentation updated if APIs changed?
  • Are there any obvious security issues (SQL injection, XSS, hardcoded secrets)?
Python — LLM review call 
async def analyze(self, diff: str) -> str:
    response = await openai.chat.completions.create(
        model="gpt-4",
        temperature=0,
        messages=[
            {"role": "system", "content": REVIEW_SYSTEM_PROMPT},
            {"role": "user", "content": f"Review this diff:\n\n{diff}"}
        ]
    )
    return response.choices[0].message.content

Specificity made all the difference. Vague prompts produce vague reviews. Specific checklists produce actionable feedback.

Lesson 1: Start With Narrow Scope

It's tempting to solve everything at once with AI. "Let's build an agent that reviews code AND suggests refactors AND finds bugs AND writes docs!"

We almost fell into that trap. Thankfully, we didn't.

We focused on one thing: catching missing tests and documentation. Nothing else. No architecture advice. No performance tips. Just the basics.

Why? Because when the agent got something wrong (and it did), the damage was small. A false alarm about missing tests is annoying. A false alarm about "rewrite your entire API" is dangerous. Start narrow. Expand later.

Lesson 2: Humans Are Still in the Loop

Here's something we got right from day one: the agent never blocks a merge.

It posts comments. That's all. Engineers can read them, ignore them, or respond to them. It never changes code. It never rejects PRs. It never auto-merges anything.

This was key for adoption. If the agent could block work, engineers would disable it. If it could modify code, they would lose trust. But a helpful assistant that posts suggestions? People loved it.

One engineer told me: "It's like having a junior reviewer who never gets tired and always remembers to check the basics."

Lesson 3: Context is Everything

Early versions had a funny problem. The agent would sometimes suggest adding tests to test files. Or complain about missing docs in config files. The input was valid, but the output was absurd.

The problem? Lack of context.

We fixed it by giving the agent more information:

  • File paths (test files vs. source files vs. config files)
  • Git history (is this a refactor or new code?)
  • PR description (what is the author trying to do?)
  • Project conventions (from a conventions.md file we created)

With better context, the reviews improved dramatically. It stopped suggesting tests for tests. It started making useful observations instead.

Lesson 4: Cost Matters

Our first month running the agent cost $847 in API calls. We were sending full file diffs for every merge request. Some reviews processed thousands of lines of code.

We optimized in three ways:

  • Smart chunking: We sent only changed sections plus a few lines of surrounding context, not entire files.
  • Caching: Repeated reviews of the same MR reused the previous analysis instead of calling the API again.
  • Model selection: We used GPT-4 for complex reviews and GPT-3.5-turbo for simple checks like "are there tests?"

After these changes, monthly costs dropped to $180. Review quality stayed the same. For a team of 30 engineers, that's $6 per person per month. A bargain compared to the time saved.

What's Next: Beyond Code Review

We're now building an Agile Planning Agent. It takes user stories and suggests technical subtasks. Early tests show it's great at catching edge cases humans forget. "What about mobile?" "Did we consider rate limiting?"

The Real Lesson: AI Agents Are Tools, Not Magic

After a year of building agents, here's my biggest takeaway. AI agents don't replace engineers. They make engineers better.

The MR Review Agent doesn't replace human reviewers. It handles the routine checks so reviewers can focus on what matters. Instead of 30 minutes checking for tests and docs, they spend 30 minutes on architecture, edge cases, and teaching moments.

The best AI agents free humans to do what humans do best. Think creatively. Make judgment calls. Build relationships.

If you're building AI agents, don't try to replace your team. Build tools that make them superhuman.

"The best tools don't replace expertise. They amplify it."

Key Takeaways:

  • Start with narrow scope — solve one problem well before expanding
  • Keep humans in the loop — agents should assist, not make decisions
  • Context is crucial — the more context you give an LLM, the better its output
  • Cost matters — optimize for both quality and API spend
  • Focus on augmentation, not replacement — make humans superhuman

AI agents work best when they help your team, not replace it. Start small, keep humans in the loop, and expand from there.
