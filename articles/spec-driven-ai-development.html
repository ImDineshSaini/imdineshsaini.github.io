Building AI features is not like building regular software. With normal code, you write tests, they pass, and you ship. With AI, the code runs fine, but the output can still be wrong or inconsistent.

I've shipped dozens of AI features. These include code review agents and document classifiers. The usual dev-test-ship cycle doesn't work well for them. You need more structure.

That's where spec-driven AI development comes in. It brings clear rules to the messy world of LLMs (Large Language Models) and machine learning.

The Problem: AI Features Are Unpredictable

This will sound familiar if you've built AI features.

You build an LLM-powered feature to sort customer support tickets. You test it by hand with 20 examples. It works great. You ship it.

Three days later, support flags a problem. The AI routed urgent billing issues to the general inquiry queue.

You dig in. The LLM read "billing urgency" as a question about billing, not an urgent problem. Your manual tests missed this edge case.

This happens because AI systems have an infinite input space. You can't test every possible input. Unit tests alone aren't enough.

The Solution: Specification-Driven Development

Spec-driven development means you define what success looks like before you write code. For AI features, that includes these five steps:

2. Build Test Cases

Let me walk you through each step.

Step 1: Write the Specification

A good AI spec answers five questions:

  • Input: What data does the system receive?
  • Output: What should it produce?
  • Success criteria: How do you measure if it worked?
  • Edge cases: What unusual inputs might break it?
  • Failure modes: What happens when it can't answer?

Here's a sample spec for a ticket classifier:

Feature: Support Ticket Classification

Input: Customer support ticket (text, 10-5000 characters)

Output: Category (Billing, Technical, General) + Urgency (Low, Medium, High, Critical)

Success Criteria: ≥95% accuracy on validation set, <2s latency

Edge Cases:
- Multilingual input
- Vague language ("something's wrong")
- Multiple issues in one ticket
- Spam/abusive language

Failure Mode: Return confidence score < 0.7 → escalate to human

Notice how specific this is. There's no room for "it mostly works."

Step 2: Build Test Cases First

Before you write any code, build a test dataset. It should cover three types of inputs:

  • Happy path examples: Clear, simple inputs (20 examples)
  • Edge cases: Ambiguous or tricky inputs (30 examples)
  • Failure cases: Inputs where the system should say "I don't know" (10 examples)

For our ticket classifier, that means hand-labeling 60 real tickets. Each one gets a category and urgency tag.

This is tedious but essential. These test cases become your ground truth. They tell you if your AI is getting better or worse.

Try It Yourself — Test Case Template
Test Dataset Plan
=================

Happy path examples (20):
- Input: [clear, simple input]
  Expected: [category] + [urgency]

Edge case examples (30):
- Input: [ambiguous or tricky input]
  Expected: [category] + [urgency]
  Note: [why this is tricky]

Failure cases (10):
- Input: [input the system should refuse]
  Expected: "I don't know" / escalate to human
Build your test dataset before writing any code.

Step 3: Implement With Validation

Now you build the feature. But you validate at every step, not just at the end:

  • After prompt engineering → run the test suite
  • After adding few-shot examples → run the test suite
  • After changing the LLM model → run the test suite
  • After adding retrieval logic → run the test suite

Each change gets checked against the spec. If accuracy drops below 95%, you don't ship.

Step 4: Automated Evaluation

You automate spec validation with test scripts. These scripts run your AI on the test dataset and check the results.

Python — Automated spec validation test 
def test_ticket_classification():
    test_cases = load_test_dataset('tickets_validation.json')

    correct = 0
    for ticket in test_cases:
        result = classify_ticket(ticket.text)
        if result.category == ticket.expected_category:
            correct += 1

    accuracy = correct / len(test_cases)
    assert accuracy >= 0.95, f"Accuracy {accuracy} below threshold"

This runs on every commit in your CI/CD pipeline. If the spec isn't met, the build fails. No exceptions.

Step 5: Production Monitoring

Your spec doesn't stop at deployment. You keep checking production against the spec criteria:

  • Accuracy drift: Sample 100 random predictions each week and validate them by hand
  • Latency: P95 latency must stay under 2 seconds
  • Confidence distribution: Track how often confidence scores drop low
  • User feedback: Add a "Was this helpful?" button on every classification

When metrics go outside spec bounds, trigger a review. Update your test dataset and retrain if needed.

Real-World Example: MR Review Agent

Here's how we used spec-driven development for our merge request (MR) review agent:

Spec:

  • Input: Git diff (up to 2000 lines)
  • Output: Review comments with line numbers and severity (info/warning/error)
  • Success Criteria: At least 80% of comments rated "helpful" by engineers
  • Edge Cases: Binary files, generated code, large refactors
  • Failure Mode: If diff exceeds 2000 lines, comment "PR too large for automated review"

Test Dataset: 50 past MRs with hand-written "gold standard" reviews.

Validation: The agent must catch at least 70% of issues that human reviewers found.

With this spec, we could measure progress clearly. After 3 rounds of improvement, we hit 82% "helpful" rating and shipped it.

Why This Works

Spec-driven development gives you three big benefits:

  • Objectivity: No more "it feels good enough." You have real numbers to check.
  • Regression prevention: Changes that break the spec get caught right away.
  • Shared understanding: Product, engineering, and QA all agree on what "done" means.

The biggest win? It shifts the question from "does it work?" to "does it meet our quality bar?"

When It Isn't Enough

This approach has limits. It won't catch everything:

  • Unknown unknowns: Edge cases you didn't think to include in your spec
  • Emergent behavior: Unexpected interactions between AI components
  • Adversarial inputs: Users who try to break the system on purpose

That's why Step 5 matters so much. Your spec should evolve as you learn from real usage. Update it often.

Getting Started

If you're building AI features, try these five steps:

  1. Pick one AI feature you're working on
  2. Write a one-page spec: input, output, success criteria, edge cases, failure modes
  3. Build a test dataset of 20-50 examples before you write code
  4. Run evaluations on every change
  5. Track production metrics against your spec

Start small. One feature, one spec. Build the habit.

"Specifications turn AI development from art into engineering."

Key Takeaways:

  • Define measurable success criteria before you build anything
  • Build test datasets that cover happy paths, edge cases, and failures
  • Validate after every change, not just at the end
  • Automate spec checks in your CI/CD pipeline
  • Monitor production metrics against your spec and update as you learn

Spec-driven development changed how I build AI features. Want to try it? Start with one feature and one spec. You'll see the difference fast.
