Multi-Cloud Reality: Why We Run on AWS, Azure, and Oracle

Multi-cloud wasn't a strategic choice for us. It was a customer requirement.

Enterprise banking clients said: "We're an Oracle shop. We won't run on AWS." Fintech startups said: "We're all-in on AWS." Government clients said: "We have Azure contracts. Use those."

So we built a banking platform that runs on AWS, Azure, and Oracle Cloud. Not because it's trendy. Because our customers demanded it.

After 3 years running multi-cloud in production, here's the brutal truth: multi-cloud is expensive, operationally complex, and rarely worth it—unless you have a specific reason.

The Multi-Cloud Spectrum

Not all "multi-cloud" strategies are the same. Here's the spectrum:

Multi-Cloud Approaches

1. Cloud-Agnostic (Portable)
Deploy same app on any cloud using abstraction layers (Kubernetes, Terraform)
Example: SaaS app runs on AWS for US, Azure for EU customers
2. Cloud-Native Multi-Cloud
Use best-of-breed services from each cloud
Example: AWS Lambda + Azure Cosmos DB + GCP BigQuery
3. Multi-Cloud Redundancy
Replicate across clouds for disaster recovery
Example: Active on AWS, failover to Azure if AWS down
4. Hybrid Cloud (Not Multi-Cloud)
On-prem + cloud (different use case)
Example: Sensitive data on-prem, compute in cloud

We use Cloud-Agnostic: same application, different clouds per customer.

Why We Went Multi-Cloud (And Why You Probably Shouldn't)

Good reasons for multi-cloud:

  • ✅ Customer requirements (our case)
  • ✅ Regulatory compliance (data sovereignty - EU data must stay in EU cloud)
  • ✅ Avoid vendor lock-in (if you're negotiating $10M+ cloud contracts)
  • ✅ Geographic coverage (cloud provider lacks presence in your target region)

Bad reasons for multi-cloud:

  • ❌ "Avoid vendor lock-in" (when you have <$100K/year cloud spend)
  • ❌ "Use best-of-breed services" (complexity >> benefits for most teams)
  • ❌ "Hedge against cloud outages" (outages are rare; multi-cloud won't save you)
  • ❌ "Negotiate better pricing" (true for huge enterprises, not SMBs)

Reality check: If you're not Fortune 500 or running a SaaS with specific customer requirements, stick to one cloud. The operational overhead isn't worth it.

System Architecture: Building Cloud-Agnostic

To run on multiple clouds, we architected for portability from day one.

Multi-Cloud Architecture

Application Layer (Cloud-Agnostic)
Node.js microservices in Docker containers
Deployed on Kubernetes (EKS / AKS / OKE)
Data Layer (Cloud-Agnostic)
PostgreSQL (RDS / Azure Database / Oracle DB)
Redis (ElastiCache / Azure Cache / OCI Cache)
Infrastructure (Cloud-Specific)
Load Balancers: ALB (AWS), App Gateway (Azure), Load Balancer (Oracle)
Managed via Terraform with modules per cloud
Observability (Cloud-Agnostic)
Prometheus/Grafana (self-hosted on Kubernetes)
Avoid cloud-specific monitoring (CloudWatch, Azure Monitor)

Key decisions:

  • Kubernetes everywhere: EKS (AWS), AKS (Azure), OKE (Oracle). Same deployment manifests.
  • Avoid cloud-specific services: No Lambda, no DynamoDB, no Azure Functions. Stick to open standards.
  • Infrastructure as Code: Terraform with cloud-specific modules, shared state.
  • Managed databases: Use cloud provider's managed Postgres (RDS/Azure DB/OCI DB) but avoid proprietary DBs.

Lesson 1: Kubernetes is Your Abstraction Layer

Kubernetes made multi-cloud possible. Same YAML manifests deploy to any cloud.

Example deployment (works on all clouds):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
      - name: payment-service
        image: payment-service:v1.2.3
        ports:
        - containerPort: 8080
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: url

Cloud-specific differences:

  • Storage classes: AWS uses gp3, Azure uses managed-premium, Oracle uses oci-bv
  • Load balancers: Service type LoadBalancer creates ALB (AWS), App Gateway (Azure), or Load Balancer (Oracle)
  • Node pools: Instance types differ (EC2 vs Azure VMs vs OCI Compute)

We handle this with Kustomize overlays:

# base/deployment.yaml (common)
apiVersion: apps/v1
kind: Deployment
...

# overlays/aws/kustomization.yaml
resources:
  - ../../base
patchesStrategicMerge:
  - storage-class-gp3.yaml

# overlays/azure/kustomization.yaml
resources:
  - ../../base
patchesStrategicMerge:
  - storage-class-premium.yaml

Lesson 2: Terraform Modules Save Sanity

Each cloud has different resource names, APIs, and quirks. Terraform abstracts this.

Directory structure:

terraform/
├── modules/
│   ├── kubernetes-cluster/  # Abstract module
│   │   ├── aws/             # EKS implementation
│   │   ├── azure/           # AKS implementation
│   │   └── oracle/          # OKE implementation
│   ├── database/
│   │   ├── aws/             # RDS implementation
│   │   ├── azure/           # Azure Database implementation
│   │   └── oracle/          # OCI DB implementation
└── environments/
    ├── aws-production/
    ├── azure-production/
    └── oracle-production/

Example: Kubernetes cluster module

# terraform/environments/aws-production/main.tf
module "kubernetes" {
  source = "../../modules/kubernetes-cluster/aws"

  cluster_name    = "banking-prod"
  node_count      = 5
  instance_type   = "m5.xlarge"
  vpc_id          = var.vpc_id
}

# terraform/environments/azure-production/main.tf
module "kubernetes" {
  source = "../../modules/kubernetes-cluster/azure"

  cluster_name    = "banking-prod"
  node_count      = 5
  instance_type   = "Standard_D4s_v3"  # Azure equivalent
  vnet_id         = var.vnet_id
}

Benefits:

  • Same parameters, different implementations
  • Easy to add new clouds (just create new module)
  • Centralized updates (change base module, affects all clouds)

Lesson 3: Data Residency is the Real Challenge

The hardest part of multi-cloud: data doesn't move between clouds easily.

Scenarios we handle:

Data Residency Patterns

Pattern 1: Isolated Per Cloud
Each cloud has own database. No cross-cloud data.
Use case: SaaS with separate tenants per cloud
Pattern 2: Cloud-to-Cloud Replication
Primary in AWS, replicate to Azure for disaster recovery
Challenge: Egress costs, latency
Pattern 3: Event-Driven Sync
Events published to cloud-agnostic message broker (Kafka)
Consumers in each cloud process events locally

We use Pattern 1 (isolated per cloud). Each customer's data lives in their chosen cloud. No cross-cloud data transfer = simpler, cheaper, compliant.

Lesson 4: Networking is a Nightmare

Networking across clouds is painful. Each cloud has different:

  • VPC/VNet concepts: AWS VPC, Azure VNet, Oracle VCN
  • Subnets & routing: Different CIDR block requirements
  • Load balancers: ALB vs App Gateway vs OCI Load Balancer
  • Egress costs: AWS charges $0.09/GB, Azure similar, Oracle free (!)

Our networking strategy:

  • No cross-cloud networking: Each cloud is isolated (no VPN between AWS-Azure)
  • Public internet for APIs: Services expose HTTPS APIs (authenticated, TLS)
  • Cloud CDN for assets: CloudFront (AWS), Azure CDN, Oracle CDN
  • Avoid private connectivity: AWS PrivateLink, Azure Private Link are cloud-specific

This simplified architecture but sacrificed some security (no private networking between clouds).

Lesson 5: Monitoring Must Be Unified

You can't use CloudWatch for AWS, Azure Monitor for Azure, Oracle Cloud Monitoring for Oracle. You'd go insane.

Our observability stack (cloud-agnostic):

  • Metrics: Prometheus (self-hosted on Kubernetes)
  • Logs: Fluentd → Elasticsearch (self-hosted or cloud-managed)
  • Tracing: OpenTelemetry → Jaeger
  • Dashboards: Grafana (unified view across clouds)
  • Alerting: Prometheus Alertmanager → PagerDuty

Key insight: Self-host observability tools on Kubernetes. Deploy same stack to all clouds. Single pane of glass.

Cost Comparison: AWS vs Azure vs Oracle

After running the same workload on all three clouds, here's what we learned:

Cloud Cost Comparison (Same Workload)

Category AWS Azure Oracle
Compute (Kubernetes) $$$ (EKS + EC2) $$$ (AKS + VMs) $$ (OKE cheaper)
Managed Database $$$ (RDS expensive) $$$ (Azure DB similar) $ (OCI DB cheapest)
Storage (Block) $$ (EBS) $$ (Managed Disks) $ (OCI cheaper)
Egress (Data Transfer) $$$ ($0.09/GB) $$$ ($0.087/GB) FREE (10TB/month)
Total (Monthly) $12,000 $11,500 $7,000

Insights:

  • Oracle is cheapest (40% cheaper than AWS for our workload)
  • AWS/Azure are similar (within 5%)
  • Egress costs matter: Oracle's free egress saved us $2K/month
  • Reserved instances: 30-50% discount if you commit (available on all clouds)

Caveat: Oracle lacks some services (managed Kafka, managed Elasticsearch). You'll self-host more, which adds operational overhead.

Real-World Migration Story

A banking client asked us to migrate from AWS to Oracle Cloud (they had Oracle database licenses, wanted consolidation).

Migration steps:

  1. Week 1: Provision Oracle Cloud infrastructure with Terraform
  2. Week 2: Deploy Kubernetes cluster (OKE), configure networking
  3. Week 3: Deploy application (same Docker images, same YAML manifests)
  4. Week 4: Migrate database (AWS RDS → Oracle Cloud Database using DMS)
  5. Week 5: Run in parallel (AWS + Oracle), compare metrics
  6. Week 6: Cutover DNS, shut down AWS resources

Total migration time: 6 weeks (with parallel runs for safety).

Downtime: Zero (DNS cutover was seamless).

Why it worked: We architected for portability from day one. If we'd used Lambda, DynamoDB, and CloudWatch, migration would've taken 6 months.

The Operational Overhead

Multi-cloud isn't free. Here's the hidden cost:

  • 3x infrastructure code: Terraform modules for AWS, Azure, Oracle
  • 3x CI/CD pipelines: Deploy to EKS, AKS, OKE
  • 3x support contracts: AWS Enterprise Support, Azure Premier, Oracle Support
  • 3x expertise required: Engineers must know all clouds
  • 3x security audits: Pen tests, compliance checks per cloud

Team impact:

  • Onboarding new engineers takes 2x longer (must learn all clouds)
  • Debugging production issues harder (which cloud is failing?)
  • Vendor negotiations more complex (can't commit to single cloud for discounts)

Our rule: Only add a new cloud if revenue justifies it (customer paying $500K+ wants specific cloud).

When Multi-Cloud Makes Sense

After 3 years, here's when I'd recommend multi-cloud:

  • ✅ SaaS with enterprise customers who demand specific clouds
  • ✅ Global compliance (GDPR requires EU data in EU cloud)
  • ✅ M&A scenarios (acquired company runs on different cloud)
  • ✅ Massive scale (negotiating $10M+ cloud contracts)

When to avoid multi-cloud:

  • ❌ You're a startup (focus on product, not infrastructure)
  • ❌ Cloud spend <$100K/year (operational overhead > savings)
  • ❌ Team <20 engineers (can't afford expertise in all clouds)
  • ❌ "Hedge against outages" (multi-cloud won't save you from application bugs)

Best Practices for Multi-Cloud

  1. Design for portability from day one: Kubernetes, open standards, avoid cloud-specific services
  2. Use Terraform extensively: IaC makes cloud differences manageable
  3. Avoid cross-cloud networking: Egress costs and complexity aren't worth it
  4. Unified observability: Self-host Prometheus/Grafana on Kubernetes
  5. Automate everything: CI/CD for Terraform, Kubernetes, application deploys
  6. Document cloud-specific quirks: AWS security groups ≠ Azure NSGs ≠ Oracle security lists
  7. Centralize secrets: Use HashiCorp Vault (cloud-agnostic), not AWS Secrets Manager

Key Takeaways

  1. Multi-cloud is expensive: 3x operational overhead. Only do it if you must.
  2. Kubernetes is your abstraction layer: Same manifests, any cloud.
  3. Terraform modules save sanity: Abstract cloud differences behind modules.
  4. Data residency is the hardest problem: Don't replicate across clouds unless necessary.
  5. Oracle is cheaper: 40% cheaper than AWS/Azure for compute + free egress.
  6. Unified observability is critical: Self-host Prometheus/Grafana, avoid cloud-specific tools.
  7. Most companies don't need multi-cloud: Single cloud + multi-region is usually enough.
