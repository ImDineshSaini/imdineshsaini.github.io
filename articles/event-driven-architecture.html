Event-Driven Architecture: Why Everything Doesn't Need to Be Synchronous

The day we moved from synchronous API calls to event-driven messaging, our system felt like it could breathe again. Response times dropped, failures became isolated, and scaling became almost trivial.

But the journey wasn't smooth. Event-driven architecture (EDA) introduces complexity most teams underestimate.

After migrating a banking platform serving millions of transactions, here's what actually works.

The Problem with Synchronous Everything

Our original microservices architecture looked clean on paper:

Synchronous Request Chain (Before)

Customer API
POST /transfer → calls Payment Service
Payment Service
→ calls Account Service → Fraud Service → Notification Service
Total Response Time
Sum of all service latencies + network overhead

The problems became obvious at scale:

  • Cascading failures: If the Notification Service went down, the entire transfer would fail (even though the payment succeeded)
  • Slow response times: Users waited 3-5 seconds while we processed notifications and fraud checks synchronously
  • Tight coupling: Adding a new step (like AML screening) meant modifying the entire request chain
  • Retry hell: When a downstream service timed out, we couldn't tell what succeeded vs. what needed retrying

The breaking point: During peak hours, our notification service would get overwhelmed. This caused payment API timeouts, leading to retries, which made everything worse.

Enter Event-Driven Architecture

Event-driven architecture flips the model: services publish events about what happened, and interested services react independently.

Event-Driven Architecture (After)

Customer API
POST /transfer → Payment Service → returns immediately (202 Accepted)
Message Broker (Kafka)
payment.initiated → payment.completed → payment.failed
Event Consumers (Parallel)
Fraud Service | Notification Service | Analytics Service | Audit Logger

Key benefits we saw immediately:

  • API response time: 3-5s → 200ms
  • Services can fail independently without affecting payments
  • Easy to add new consumers (just subscribe to events)
  • Natural audit trail (all events logged)

System Design: Choosing the Right Message Broker

Not all message brokers are created equal. Here's what we evaluated:

Message Broker Comparison

Broker Best For Trade-offs
Kafka High-throughput, event sourcing, replay Complex ops, eventual consistency
RabbitMQ Traditional messaging, complex routing Lower throughput, no built-in replay
AWS SQS/SNS Serverless, simple pub/sub Limited ordering, cloud lock-in
Redis Streams Low latency, simple use cases Not durable for long-term storage

We chose Kafka for banking transactions because:

  • Event replay: Regulatory requirement to replay transactions for audits
  • Ordering guarantees: Partition-level ordering for account operations
  • Throughput: Handle 50K+ events/second during peak
  • Retention: Store events for 30+ days for compliance

Architecture Pattern: Event Sourcing vs. Event-Driven

There's confusion between Event-Driven Architecture and Event Sourcing. They're related but different:

EDA vs. Event Sourcing

Event-Driven Architecture (EDA)
Services communicate via events. State is stored in traditional databases.
Example: Payment completed → Send notification event
Event Sourcing
Events are the source of truth. Application state is derived by replaying events.
Example: Account balance = replay all deposit/withdrawal events

We use EDA for most services (simpler, easier to reason about), and Event Sourcing for critical financial ledgers (full audit trail, time-travel debugging).

Lesson 1: Design Events, Not Commands

Early mistake: We designed events like RPC calls.

Bad (Command-style):

{
  "event": "send_notification",
  "userId": "123",
  "message": "Your payment succeeded"
}

Good (Event-style):

{
  "event": "payment.completed",
  "paymentId": "pay_abc123",
  "userId": "123",
  "amount": 50.00,
  "timestamp": "2025-08-29T10:30:00Z"
}

Why? Events describe what happened, not what should happen next. This lets multiple consumers react differently:

  • Notification Service sends an email
  • Fraud Service updates risk scores
  • Analytics Service logs metrics
  • Future services can subscribe without changing existing code

Lesson 2: Handle Idempotency from Day One

In distributed systems, events can be delivered multiple times. Your consumers must be idempotent.

We learned this the hard way when a Kafka rebalance caused duplicate payment notifications. Users got 5 emails saying "Payment completed!"

Our idempotency pattern:

async function handlePaymentCompleted(event) {
  const eventId = event.id; // Unique event ID

  // Check if we've processed this event before
  const processed = await redis.get(`processed:${eventId}`);
  if (processed) {
    logger.info('Event already processed, skipping');
    return;
  }

  // Process the event
  await sendNotification(event.userId, event.amount);

  // Mark as processed (with TTL)
  await redis.setex(`processed:${eventId}`, 86400, 'true');
}

Key points:

  • Every event gets a unique ID
  • Check if processed before doing work
  • Use TTL on the processed flag (don't store forever)
  • For critical operations (like payments), use database transactions with unique constraints

Lesson 3: Dead Letter Queues Save Lives

Not all events will process successfully. Maybe the service is down, maybe the data is corrupted, maybe there's a bug.

Without a strategy, failed events just... disappear.

Our retry & DLQ strategy:

Retry and Dead Letter Queue Flow

1. Initial Processing
Consumer tries to process event
2. Transient Failure (e.g., network timeout)
Retry 3 times with exponential backoff (1s, 2s, 4s)
3. Persistent Failure
Send to Dead Letter Queue (DLQ)
4. Manual Review
Alerts sent to on-call, team investigates DLQ

We monitor DLQ depth. If it spikes, something's wrong (bad deploy, service outage, data quality issue).

Lesson 4: Schema Evolution is Critical

Events are contracts between services. When you change an event schema, you risk breaking consumers.

We use Schema Registry (Confluent) with these rules:

  • Backward compatible: New producers, old consumers must work
  • Forward compatible: Old producers, new consumers must work
  • Version events: Include schema version in every message
  • Use Avro or Protobuf: Enforces schema contracts, better than JSON

Example schema evolution:

// Version 1
{
  "paymentId": "pay_123",
  "amount": 50.00
}

// Version 2 (added optional field - backward compatible)
{
  "paymentId": "pay_123",
  "amount": 50.00,
  "currency": "USD"  // New field with default value
}

When NOT to Use Events

Event-driven isn't a silver bullet. Don't use events when:

  • You need immediate feedback: Login, authentication should be synchronous
  • Strong consistency required: Critical balance checks (use database transactions)
  • Simple request-response: Fetching user profile doesn't need events
  • Low event volume: If you have 10 events/day, don't introduce Kafka complexity

Our rule: Commands are synchronous, notifications are asynchronous.

System Design: Handling Failures Gracefully

In EDA, you trade consistency for availability. Here's how we handle the trade-offs:

Saga Pattern for Distributed Transactions

Happy Path
1. Debit account → 2. Credit account → 3. Send notification → ✓ Done
Failure Scenario (Step 2 fails)
1. Debit account → 2. Credit fails → 3. Compensate: Refund debit → 4. Send failure notification

For complex workflows, we use the Saga pattern:

  • Each step publishes success/failure events
  • Compensating transactions undo partial work
  • Orchestrator (or choreography) coordinates the flow

Monitoring Event-Driven Systems

Observability is harder in EDA. You can't just trace a single HTTP request.

Our observability stack:

  • Correlation IDs: Every event includes a trace ID linking related events
  • Kafka lag monitoring: Alert if consumers fall behind (SLO: < 30s lag)
  • Event schema validation: Reject malformed events at the broker
  • Consumer health checks: Detect if a consumer stops processing
  • Distributed tracing: OpenTelemetry to trace events across services

We use Datadog for metrics and Jaeger for distributed tracing.

The Results

After migrating to event-driven architecture:

  • API latency: 3-5s → 200ms (15x faster)
  • Failure isolation: Notification service outages don't block payments
  • Deployment velocity: Services deploy independently, 20+ deploys/day
  • Feature development: New features subscribe to existing events, no code changes to producers
  • Scalability: Consumer groups scale independently based on load

Trade-offs we accepted:

  • Eventual consistency: Users see "Payment processing" instead of instant confirmation
  • Operational complexity: Kafka cluster requires dedicated ops attention
  • Debugging difficulty: Tracing event flows is harder than HTTP traces
  • Ordering challenges: Had to carefully design partition keys for ordering guarantees

Key Takeaways

  1. Start small: Don't migrate everything to events. Start with non-critical notifications.
  2. Design events, not commands: Events describe what happened, not what should happen.
  3. Idempotency is mandatory: Events will be delivered multiple times. Handle it.
  4. Schema evolution matters: Use Schema Registry and enforce compatibility rules.
  5. Monitor relentlessly: Consumer lag, DLQ depth, and correlation IDs are your best friends.
  6. Know when NOT to use events: Synchronous is still the right choice for many scenarios.
